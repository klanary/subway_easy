# 13. 화면 상태 모델, 표시 형식, 내비게이션 뼈대

- 무엇을 만들었나: 모든 데이터 화면이 쓰는 다섯 상태(`UiState`: 로딩·내용·빈 결과·오류·오프라인)와 그 공통 화면(`StateContainer`), 서버 결과를 화면 상태로 바꾸는 `toUiState`, 시간·요금·거리 표시 형식, 타입 안전 내비게이션 목적지와 자리 표시 화면, 검색 결과를 이전 화면에 돌려주는 `PickResult`, 컨테이너에서 ViewModel을 만드는 `appViewModel`.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 화면마다 로딩·오류 처리를 따로 그리면 모양과 문구가 제각각이 된다. 상태를 봉인 인터페이스 하나로 정하고 공통 컨테이너가 내용 외 네 상태를 그리게 해, 화면은 "내용"만 신경 쓴다.
  - 서버가 만료 캐시로 응답(`stale`)하면 내용을 흐리게(알파 0.5) 하고 "갱신 지연"을 붙인다. 아무것도 안 보여주는 것보다 지난 정보라도 보여주는 편이 통학 중에 쓸모 있다(스펙 4.5).
  - 남은 시간은 내림(119초 → "1분"), 소요 시간은 올림(59초 → "1분")이다. 열차는 실제보다 늦게 오는 것처럼 보이면 놓칠 수 있고, 이동 시간은 짧게 보이면 늦는다. 둘 다 사용자에게 안전한 쪽으로 반올림했다.
  - 내비게이션은 문자열 경로 대신 `@Serializable` 클래스로 목적지를 정했다(Navigation 2.8+의 타입 안전 경로). 인자 이름·타입 실수가 컴파일 단계에서 잡힌다.
  - 검색 화면이 고른 결과는 이전 화면의 `SavedStateHandle`에 JSON으로 넣고 돌아간다. 화면끼리 ViewModel을 공유하지 않아도 되고, 결과를 꺼낸 뒤 지워 한 번만 처리된다.
- 막혔던 점과 해결:
  - 요금의 천 단위 구분과 거리의 소수점은 지역 설정에 따라 달라진다(독일은 "1.550"). 요금은 `Locale.KOREA`, 거리는 `Locale.US`로 형식을 고정했다.
  - 개발 PC에 에뮬레이터·실기기가 없어 "홈 자리 표시 화면이 뜬다"는 확인은 하지 못했다. 빌드와 단위 테스트만 확인했다.
- 예상 면접 질문과 내 답:
  - Q. 왜 상태를 봉인 인터페이스로 만들었나요? A. `when`이 다섯 경우를 모두 다뤘는지 컴파일러가 확인한다. 새 상태를 추가하면 처리하지 않은 화면이 컴파일 오류로 드러난다.
