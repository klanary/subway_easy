# 35. 열차 위치 API 데이터와 계획한 열차 번호

> Claude Code가 쓴 초안이다. 본인이 직접 고쳐 쓴다(스펙 12절).

- 무엇을 만들었나: 서버의 새 응답 형식을 읽는 DTO(`TrainNearDto`, `LineTrainsDto`, `TrainEtaDto`, `TrainState`), 도착 정보 열차의 `trainNo`·`basis` 칸, 두 API(`lineTrains`, `trainEta`)와 저장소 `TrainRepository`, 승차 전 알림 계획(`TrainPlan`)에 저장하는 열차 번호.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 새 칸은 모두 기본값이 있다. 아직 새 칸을 보내지 않는 예전 서버, 그리고 업데이트 전에 저장된 세션 JSON도 그대로 읽혀야 하기 때문이다(위치 결합 스펙 6.3, 7.4).
  - 열차 번호는 서울시 도착정보(`btrainNo`)와 위치정보(`trainNo`)를 잇는 열쇠다. 승차 전 알림이 고른 열차의 번호를 계획에 넣어 두면, 사용자가 [탑승했어요]만 눌러도 "그 열차에 탔다"고 보고 추적을 시작할 수 있다(스펙 7.1 계획한 열차).
  - 저장소는 다른 저장소처럼 `ApiCaller`로 감싸 오류를 `ApiResult`로 바꾼다. 화면과 세션 코드는 예외 대신 결과 값만 다룬다.
- 막혔던 점과 해결:
  - `ApiService`에 메서드를 더하자 그것을 직접 구현한 테스트용 가짜(`RecordingApiService`)가 컴파일되지 않았다. 쓰지 않는 메서드는 `error("not used")`로 채웠다.
- 예상 면접 질문과 내 답:
  - Q. 서버가 새 칸을 보내기 전에 앱을 먼저 배포하면? A. 새 칸에 기본값(null)이 있고 JSON 설정이 모르는 키를 무시하므로 둘 다 문제없이 동작한다.
  - Q. `TrainState`를 문자열 대신 enum으로 둔 이유는? A. 서버가 보내는 값이 네 가지로 정해져 있고, enum이면 `when`에서 빠진 경우를 컴파일러가 잡아 준다.
