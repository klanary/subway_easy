# 93. 서버 전체 리뷰 반영: IP 위조, 429, 밤 시간표, 오래된 실시간

> Claude Code가 쓴 초안이다. 본인이 직접 고쳐 쓴다(스펙 12절).

- 무엇을 만들었나: 2026-11-17 서버 전체 리뷰에서 나온 7건을 고쳤다.
  1. 요청 제한의 IP를 `X-Forwarded-For`의 첫 값이 아니라 마지막 값으로 정한다. 첫 값은 보내는 쪽이 마음대로 넣어 요청마다 바꾸면 제한을 피할 수 있었다.
  2. HTTP 429를 받으면 그날 하루를 멈추던 것을 60초만 쉬게 했다(`QuotaGuard.pause`). 쉬는 동안의 안내 문구도 "내일 다시"가 아니라 "1분 뒤 다시"다(`QUOTA_EXCEEDED`/`PAUSED`).
  3. 시간표: 그날 열차가 모자라면(밤늦게) 다음 날 시간표에서 채운다. 23:58에 4대를 물으면 자정 넘은 3대 + 다음 날 첫차.
  4. 실시간: 생성 시각(`recptnDt`)이 미래면 지금으로 보고, 10분보다 오래된 항목은 뺀다. 미래 160초면 2분 뒤 열차가 4분 40초로, 18분 늦은 정보면 지나간 열차가 "곧 도착"으로 보였다.
  5. 새벽에 전날·오늘 시간표 가운데 하나만 실패하면 나머지로 답한다.
  6. 경로 5개에 열차를 붙이는 일을 동시에 한다.
  7. `/v1/metrics`는 `METRICS_TOKEN`을 아는 사람만 본다.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 429를 그냥 일시 오류로 재시도하는 방법도 있었다. 하지만 카카오는 하루 한도 초과도 429로 알린다. 재시도하면 한도가 찬 날 요청마다 두 번씩 부른다. 60초 쉬기는 두 경우 모두에 맞는다. 한도 초과면 1분에 한 번만 다시 확인하게 된다.
  - 다음 날 시간표는 늘 부르지 않고 "모자랄 때만" 부른다. 낮에는 추가 호출이 없다.
  - 오래된 실시간을 시간표로 바꾸지 않고 그냥 뺐다. 그 방향 실시간이 다 빠지면 기존 규칙대로 시간표가 채운다.
  - 지표를 아예 지우지 않고 토큰으로 막았다. 부하 테스트와 운영 확인에 계속 쓴다. 토큰을 정하지 않은 서버는 지표가 닫혀 있는 것이 기본이다.
- 막혔던 점과 해결:
  - respx에는 `url__endswith` 조건이 없어 `url__regex`로 바꿨다.
  - 경로 동시 처리는 새 테스트 없이 기존 경로 테스트(48개)로 결과가 같은지만 확인했다. 같은 역의 실시간·시간표 호출은 캐시의 "진행 중 호출 합치기"가 한 번으로 묶는다.
- 예상 면접 질문과 내 답:
  - Q. 프록시 뒤에서 클라이언트 IP를 어떻게 믿을 수 있게 구하나?
  - A. `X-Forwarded-For`는 각 프록시가 받은 주소를 뒤에 붙인다. 믿을 수 있는 건 내 쪽 프록시가 붙인 값뿐이다. 프록시가 하나면 마지막 값을 쓴다. 여러 겹이면 믿는 프록시 수만큼 뒤에서 센다.
