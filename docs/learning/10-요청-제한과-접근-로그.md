# 10. IP별 요청 제한, 요청 ID, JSON 접근 로그

- 무엇을 만들었나: IP별 분당 60회 슬라이딩 윈도우 요청 제한(`SlidingWindowRateLimiter`), 모든 요청에 붙는 요청 ID(`X-Request-ID`), `/v1/` 요청 수·제한 횟수 지표, 쿼리를 뺀 한 줄 JSON 접근 로그.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 고정 윈도우(매 분 0초에 초기화)는 59초와 61초 사이에 한도의 두 배가 몰릴 수 있다. 슬라이딩 윈도우는 "지금부터 60초 전까지"를 세므로 그런 구멍이 없다. IP마다 요청 시각을 `deque`에 넣고, 창 밖 기록을 앞에서 빼는 방식이라 연산이 가볍다.
  - Render 같은 호스팅은 프록시 뒤에서 앱을 돌리므로 직접 보이는 IP는 프록시 IP다. `X-Forwarded-For`의 첫 번째 값을 실제 사용자 IP로 쓴다.
  - `/health`는 제한하지 않는다. 호스팅 헬스 체크와 잠듦 방지 호출이 막히면 서비스가 재시작될 수 있다(스펙 6.8).
  - 접근 로그에는 경로만 남기고 쿼리는 뺀다. 쿼리에는 좌표와 검색어가 들어간다(개인정보 원칙, 스펙 5.4).
  - 다시 오지 않는 IP의 기록이 계속 쌓이지 않도록, 창 한 번마다 마지막 요청이 창 밖인 키를 지운다.
- 막혔던 점과 해결:
  - 계획의 미들웨어 테스트는 역 검색 API(`/v1/stations/search`, P2 Task 4)를 불렀는데, 그 API는 역 원본 데이터가 있어야 만들 수 있다. 미들웨어만 검증하면 되므로 테스트 안에서 `/v1/_probe` 경로를 추가해 썼다.
  - 계획의 테스트 `all((await ...) for _ in range(10))`은 실행되지 않았다. 비동기 함수 안에서 `await`가 든 제너레이터 식은 비동기 제너레이터가 되어 `all()`에 넣을 수 없다. 리스트 내포로 바꿨다.
- 예상 면접 질문과 내 답:
  - Q. X-Forwarded-For는 조작할 수 있지 않나요? A. 맞다. 사용자가 헤더를 직접 넣으면 첫 값을 바꿀 수 있다. 정확히 하려면 신뢰하는 프록시가 붙인 값만 오른쪽부터 세야 한다. 1차에서는 무료 호스팅의 남용 방지가 목적이라 단순한 방식을 썼고, 외부 API 한도는 호출 한도 보호(07)가 따로 지킨다.
  - Q. 서버가 여러 대면? A. 메모리 기록이 서버마다 따로라 제한이 느슨해진다. Redis의 정렬 집합(ZSET)으로 옮기면 같은 슬라이딩 윈도우를 공유할 수 있다.
