# 63. 수집 DB와 위치 응답 해석

> Claude Code가 쓴 초안이다. 본인이 직접 고쳐 쓴다(스펙 12절).

- 무엇을 만들었나: `server/ml/parse.py`(위치 API 응답 → `Event`, 서비스 날짜, 이상값 표시)와 `server/ml/store.py`(SQLite 표 4개: `raw_snapshots`, `events`, `station_map`, `key_usage`). 실제 5호선 응답을 `tests/fixtures/seoul_position_line5.json`으로 남겼다.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 중복 제거는 SQL 한 문장으로 했다: `INSERT … ON CONFLICT(운행일, 호선, 열차, 역, 상태) DO UPDATE … WHERE excluded.event_at < events.event_at`. "가장 이른 `recptnDt`를 남긴다"는 규칙이 DB 안에서 지켜지므로 수집기가 두 번 떠도 깨지지 않는다. `first_seen_at`은 갱신하지 않는다.
  - 시각은 모두 KST ISO 8601 글자로 쓴다. 꼴이 같으면 글자 비교가 시간 비교와 같아서 위 `WHERE`가 맞는다.
  - raw 응답은 zlib으로 눌러 BLOB으로 둔다. 하루 약 4.6만 건이고 본문에 `null` 칸이 많아 10분의 1쯤으로 준다. 파싱 규칙을 바꿔도 다시 만들 수 있게 원문을 그대로 둔다.
  - 요일 구분은 서버의 `week_tag`(1 평일, 2 토, 3 휴일)를 그대로 쓴다. 시간표 API의 `WEEK_TAG`와 같아서 나중에 공식 시간표(B0)와 바로 맞춘다.
  - 이상값(`future`: 받은 시각 +30초 넘음, `stale`: 10분 넘게 오래됨)은 `flag`만 달고 지우지 않는다.
- 막혔던 점과 해결:
  - "새로 들어간 행 수"를 세려고 `COUNT(*)`를 쓰면 표가 커질수록 느려진다. 새 행만 rowid가 커지므로 `rowid > 직전 최댓값`으로 센다.
  - 서비스 날짜는 01시 전이면 전날이다. 요일 구분도 그 날짜 기준이어야 해서(월요일 00:30은 일요일 운행) 날짜를 먼저 구하고 `week_tag`를 부른다.
  - 응답 코드는 정상일 때 `errorMessage.code`, 데이터 없음·오류일 때는 본문 바로 아래 `code`에 온다. 둘 다 읽는다.
- 예상 면접 질문과 내 답:
  - Q. 원문(raw)과 정리한 표(events)를 둘 다 두는 이유는?
  - A. 정리 규칙이 틀렸을 때 다시 만들 수 있어야 하기 때문이다. 원문은 크지만 압축하고 보관 기간(14일)을 두면 감당할 수 있다. 정리한 표는 분석이 바로 읽는 모양이다.
