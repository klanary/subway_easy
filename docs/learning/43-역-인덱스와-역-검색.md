# 43. 역 인덱스와 역 검색 API

> Claude Code가 쓴 초안이다. 본인이 직접 고쳐 쓴다(스펙 12절).

- 무엇을 만들었나: `stations.sqlite`를 서버 시작 때 메모리에 올리는 `StationIndex`(역 찾기, 이름·초성 검색, 가장 가까운 역)와 `GET /v1/stations/search`.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 역은 655개뿐이라 요청마다 SQLite를 조회하지 않고 메모리에 올린다. 검색은 전체를 훑어도 충분히 빠르고, 외부 API를 부르지 않아 호출 한도와 무관하다.
  - 검색 순위는 완전 일치 > 앞부분 일치 > 포함이고, 같으면 호선이 많은 역(환승역)을 먼저 보인다. "서울"을 치면 서울역이 먼저, "입구"를 치면 홍대입구가 먼저 나온다.
  - 검색어가 모두 한글 자음이면 초성 열에서 찾는다("ㅎㄷㅇㄱ" → 홍대입구).
  - `resolve`는 다른 출처의 역 이름을 우리 역으로 바꾼다. 카카오 경로는 "경복궁(정부서울청사)", 실시간 API는 "서울"처럼 표기가 달라서, 정규화한 이름 → 별칭 순으로 찾는다. 이름이 같은 역이 여럿이면(양평) 그 단계의 호선을 가진 역을 고른다.
- 막혔던 점과 해결:
  - 실제 역 데이터를 받아 보니 호선 칸이 운영 호선이 아니라 선로 이름(경부선, 경원선, 일산선)이었다. 그대로 두면 수원역이 "경부선"으로 나오고 실시간 API의 "1호선"과 맞지 않는다. 변환 표를 두고, 경원선처럼 역에 따라 호선이 갈리는 곳은 행 보정 표로 고쳤다.
  - 합성 데이터 테스트만으로는 이 문제를 알 수 없었다. 실제 데이터로 돌려 보는 테스트(`real_index`)를 더했다.
- 예상 면접 질문과 내 답:
  - Q. 역이 수만 개로 늘면? A. 지금 구조는 전체 탐색이라 느려진다. 그때는 SQLite FTS나 접두어 인덱스로 바꾼다. 지금 규모에서는 단순한 쪽이 낫다.
  - Q. 잘못된 요청은 어떻게 처리하나? A. 검색어는 공백을 뺀 뒤 1~50자, 개수는 1~50이어야 하고, 어기면 400과 정해진 오류 형식(`INVALID_REQUEST`)을 돌려준다.
