# 재설계: 2026-11-11부터 제출까지

> **2026-11-12:** 범위와 일정은 [간단한 지하철 앱 재설계 스펙](../specs/2026-11-12-simple-subway-redesign.md)으로 다시 정했다. 이 문서의 1절(점검 결과)과 원칙은 유효하고, 3·4절의 단계와 범위는 그 스펙 11절이 대신한다.

2026-11-11에 지금까지의 작업과 설계를 점검하고 남은 일정을 다시 짰다. 이 문서가 P1~P6의 **순서와 범위**를 대신한다. 각 작업의 내용(파일, 인터페이스, 테스트)은 원래 계획 문서를 그대로 따른다.

## 1. 점검 결과

| 영역 | 2026-11-11 상태 |
|---|---|
| 앱 | 화면(P3), 통학 세션(P4 Task 1~9, 11, 12), 열차 추적(P6 Task 8~14)까지 구현. 단위 테스트 258개 통과. **기기에서 실행한 적 없음** |
| 서버 | 기반(P2 Task 1, 2, 5~8, 13, 14)만 있음. 엔드포인트는 `/health`, `/v1/metrics`뿐. 역 검색·실시간 도착·장소 검색·경로 API 없음 |
| 1단계 확인 | 하지 않음. `api-verification.md`, `original-app.md`, `ux-comparison.md`가 빈 양식이었음 |
| 저장소 | 쌓인 PR 10개가 열린 채였고 `main`은 첫 커밋뿐 |

### 무엇이 잘못됐나

1. **1단계 확인(스펙 14절)을 건너뛰었다.** 스펙은 "구현 전에 모두 확인"이라고 했지만, 앱의 데이터 형식은 실제 응답이 아니라 스펙의 가정 위에 만들어졌다.
2. **순서가 뒤집혔다.** 스펙 11절은 서버 다음에 앱인데, 앱이 끝까지 가는 동안 서버는 기반에 머물렀다. 그래서 실제 데이터로 동작한 흐름이 하나도 없다.
3. **기본이 끝나기 전에 범위를 넓혔다.** 11/5에 위치 결합(P6, 작업 14개)을 더했고, 앱은 아직 없는 서버 API(`/v1/lines/{line}/trains`, `/v1/trains/{trainNo}`)를 부른다.
4. **"키가 없어 막혔다"는 판단이 과했다.** 서울시 공식 샘플 키로 '서울'역의 실제 응답을 받을 수 있고, 카카오 경로 API의 주소와 형식은 공식 문서에 있다.
5. **쌓인 PR이 멈췄다.** 9일 동안 하나도 머지되지 않았다.
6. **성공 기준 S4(통학에 2주 이상 사용)는 남은 기간으로 채울 수 없다.**

스펙의 기능 설계 자체에서는 고칠 결함을 찾지 못했다. 카카오 대중교통 경로 API(`GET https://dapi.kakao.com/v2/routing/publictraffic`)는 실제로 있고 파라미터도 스펙과 같다.

## 2. 원칙

- **새 기능은 멈춘다.** 남은 일은 "이미 만든 앱이 실제 데이터로 돌게 하는 것"이다.
- **세로로 한 줄기씩.** 서버 기능 하나를 만들면 바로 실기기에서 그 화면을 실제 데이터로 확인한다. 확인 전에는 다음 줄기로 가지 않는다.
- **통합 브랜치 하나.** `develop`(`feat/via-cloud` + `feat/server-infra`)에서 이어 가고, 줄기마다 `develop`으로 가는 작은 PR을 만든다. 기존 PR #1~#10은 `develop`을 `main`에 합친 뒤 닫는다.
- **확인이 먼저.** 외부 API를 쓰는 작업은 실제 응답 샘플(`server/tests/fixtures/`)을 받고 `api-verification.md`에 적은 뒤 시작한다.
- **11/23에 기능 개발을 멈춘다**(스펙 11절 그대로).

## 5. 2026-11-11에 확인한 사실과 그에 따른 변경

자세한 값은 `docs/analysis/api-verification.md`에 있다.

| 사실 | 영향을 받는 작업 |
|---|---|
| 서울시 API는 오류도 HTTP 200으로 준다. 정상은 `errorMessage` 안에 `INFO-000`, 오류는 `errorMessage` 없이 `code: ERROR-…`가 바로 온다 | P2 Task 9의 클라이언트는 두 형식을 모두 읽는다 |
| 샘플 5행 중 4행의 `barvlDt`가 `"0"`이고, 같은 응답 안에 6분 넘게 묵은 행이 있다 | P2 Task 8·9, P6 Task 2의 보정 규칙이 필요하다는 근거 |
| 샘플 키는 '서울'역 0~5행만 된다 | 나머지 샘플(환승역, 이름 예외 역, 데이터 없음, 한도 초과)은 본인 키가 있어야 한다 |
| 역 데이터는 서울시 OpenAPI `subwayStationMaster`로도 받을 수 있다(784행, 열 `BLDN_ID`, `BLDN_NM`, `LAT`, `LOT`, `ROUTE`). 샘플 키는 5행까지 | P2 Task 3은 파일 대신 일반 인증키로 받은 JSON을 입력으로 써도 된다 |
| 카카오 경로 API: `GET https://dapi.kakao.com/v2/routing/publictraffic`. 정차역은 이름만 있고, 경유지·출발 시각 파라미터는 없다 | `KAKAO_ROUTE_URL`을 채웠다. P2 Task 11은 본인 키로 받은 샘플로 필드 대응표를 확정한 뒤 시작한다 |
| 카카오 앱이 "테스트앱"이면 하루 쿼터가 아주 작아 `code: -10`이 온다 | 스펙 14절 확인 항목에 추가 |
