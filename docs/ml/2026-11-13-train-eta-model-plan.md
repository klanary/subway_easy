## 1. 왜 만드나 — 바뀐 우선순위

"지금 몇 분 뒤"는 실시간 도착 API를 더 자주 부르면 해결된다(한도가 풀렸으므로). 모델의 가치는 **실시간 API가 아예 주지 않는 것**에 있다.

| 순위 | 쓰임 | 지금 | 모델이 줄 것 |
|---|---|---|---|
| 1 | **실측 시간표**: 시간표 API가 없는 노선(1호선, 경의중앙선, 수인분당선, 신분당선, 공항철도, 경춘선, 우이신설선, 신림선, 경강선, 서해선, GTX-A — 시간표 API는 2~9호선만)의 미래 시각 | "+1시간", 시각 선택, 루틴 미리보기, 경로 `departAt`, 환승 열차, 막차 확인이 비어 있음 | 관측으로 만든 (요일 구분·호선·방향·역)별 출발 시각표 |
| 2 | **내가 탄 열차**: 열차 번호로 환승역·하차역 도착 시각 예측 | 없음 | 마지막 위치 + 학습한 구간·정차 시간 |
| 3 | 루틴 **"지금 출발하세요" 알림을 미리 설정**, **"평소보다 늦음"** 알림 | 실시간이 잡힐 때만 | 실측 시간표(미리 설정) + 그날 지연과 평소 분포 비교 |
| 부수 | 위치 데이터 이상값 거르기 | 없음 | 학습한 구간 시간으로 오래되거나 미래인 `recptnDt`, 늘 "도착"인 강일, 빠진 천호 같은 값을 걸러 냄 |

### 목표·비목표·실패 조건

- 목표: 역 S, 호선 L, 방향 D, 기준 시각 t(미래 포함)가 주어지면 t 이후 출발하는 열차 2~4대의 예상 시각과, 열차 번호가 주어지면 하류 역 도착 예상 시각을 준다. 응답 `source`에 `"predicted"`를 더한다.
- 비목표: 실시간이 있는 "지금 다음 열차"를 대체하지 않는다. 딥러닝은 쓰지 않는다. 사용자 위치·기록은 모으지 않는다(공개 열차 데이터만).
- 실패 조건: 수집기가 서버 키를 써서 앱이 멈춤 / 키 값이 로그·DB·커밋에 남음 / 관측이 적은데 예측을 보여 줘서 공식 시간표(B0)보다 틀림.

## 2. 데이터 수집

### 2.1 출처: 서울시 실시간 열차 위치정보(`realtimePosition`)

- 요청: `http://swopenapi.seoul.go.kr/api/subway/{키}/json/realtimePosition/0/200/{호선명}`. 한 번에 그 호선의 모든 열차.
- 쓸 필드: `trainNo`, `statnId`/`statnNm`(지금 역), `trainSttus`(0 진입, 1 도착, 2 출발, 3 전역출발), `recptnDt`(이벤트 시각), `updnLine`(`"0"` 상행·내선, `"1"` 하행·외선), `statnTid`/`statnTnm`(종착역), `directAt`(1 급행, 7 특급), `lstcarAt`(1 막차).
- 알려진 문제: `recptnDt`가 오래되거나(실측 18분) 미래로(최대 +160초) 옴. 5호선 천호 누락, 강일은 늘 "도착". 6호선 위치가 자주 빠짐. 0시 30분 이후 1~8호선 정보가 사라짐. 큰 페이지에서도 열차 일부가 빠짐.
- 응답 코드: `INFO-000` 정상, `INFO-200` 데이터 없음(빈 목록, 오류 아님), `ERROR-337` 일일 한도 초과, 그 밖 `ERROR-3xx` 요청 오류, `5xx/6xx` 서버 오류.

### 2.2 호출량과 키(개정)

- 한도가 풀렸으므로 "1,000회/일, 2~3개 호선" 가정을 버린다.
- 대상 호선 약 19개(1~9호선 + §1 표의 노선) × 30초 간격 × 20시간 = 하루 약 **4.6만 회**.
- 키 순서: **위치 키(`SEOUL_POSITION_API_KEY`) → 예비 1(`SEOUL_SPARE_KEY_1`) → 예비 2(`SEOUL_SPARE_KEY_2`)**. 한 키가 `ERROR-337`이면 그 키는 그날(KST 자정까지) 쉬고 다음 키로 넘긴다. 세 키가 모두 막히면 그날 수집을 멈춘다.
- **서버가 쓰는 `SEOUL_REALTIME_API_KEY`는 수집기가 절대 쓰지 않는다.** `SEOUL_OPENAPI_KEY`도 쓰지 않는다.
- 키별·날짜별 호출 수, 오류 수, 337 발생 시각을 DB(`key_usage` 표)에 남긴다. 키는 이름(`position`, `spare1`, `spare2`)으로만 기록한다.
- 호선별로 한 번에 하나씩 부르고, 30초 주기 안에 고르게 흩어 부른다(한꺼번에 19개를 쏘지 않는다).

### 2.3 수집기를 돌릴 곳(개정)

- **무료 상시 VM**(리눅스). `systemd` 서비스로 띄우고 `Restart=always`. 시간대는 KST로 맞춘다.
- 스크립트는 OS에 묶이지 않는 순수 Python(서버와 같은 가상 환경·의존성). 개발 PC(Windows)에서도 같은 명령으로 돌아야 한다. VM 준비 전과 첫 1시간 확인은 개발 PC에서 한다.
- 매일 백업: 전날 SQLite를 `sqlite3 .backup`(또는 Python `Connection.backup`)으로 날짜 붙은 파일로 복사하고 gzip. 보관 위치와 VM 밖으로 옮기는 방법은 `docs/ml/collector.md`에 적는다.
- Render 무료 서버(잠듦)와 GitHub Actions cron(최소 5분, 지연)은 쓰지 않는다.

### 2.4 저장 형식

- SQLite 한 파일(기본 `server/ml_data/collector.sqlite`, `.gitignore`에 넣음). 커지면 날짜별 Parquet로 옮긴다(나중).
- `raw_snapshots`(호선, 받은 시각, 결과 코드, 응답 JSON 그대로): 파싱 규칙을 바꿔도 다시 만들 수 있게 한다. 키·URL은 저장하지 않는다.
- `events`(서비스 날짜, 요일 구분[평일·토·휴일, `holidays` KR], 호선, 방향, `trainNo`, 우리 역 id, 실시간 `statnId`, 상태[진입·도착·출발·전역출발], 이벤트 시각, 처음 본 시각, 종착역, 급행, 막차).
  - 중복 제거 키 `(서비스 날짜, 호선, trainNo, 역, 상태)`. 같은 키가 다시 오면 **가장 이른 `recptnDt`를 남긴다**.
  - 서비스 날짜: 01시 이전 이벤트는 전날로 친다(막차가 자정을 넘으므로).
  - 이상값은 지우지 않고 표시만 한다: `recptnDt`가 받은 시각보다 미래(+30초 넘음)이거나 10분 넘게 오래됨 → `flag`. 구간 시간을 배운 뒤에는 그 분포를 벗어나는 값에도 표시한다(§4 B2).
- `station_map`(호선, `statnId`, `statnNm`, 우리 역 id 또는 NULL, 처음 본 날). 역 이름은 `StationIndex.resolve(statnNm, 호선)`로 잇는다. 이을 수 없는 이름은 NULL로 남기고 매일 목록을 로그로 남긴다(별칭 추가용).
- `key_usage`(날짜, 키 이름, 호출 수, 오류 수, 337 시각).
- 로그와 예외 메시지의 URL은 `app.clients.http.mask_url`을 거친다. 키는 이름으로만 `server/.env`(VM에서는 같은 위치의 `.env`)에서 읽는다.

## 3. 수집 첫 주에 확인할 것

1. 같은 시간표 칸의 열차가 날마다 같은 `trainNo`를 쓰는가(같은 요일 구분 기준)? 그렇다면 "열차 번호별 실측 시간표"가 가장 단순하고 강하다.
2. 정차 시간(도착→출발)과 역 사이 이동 시간(출발→다음 역 도착)의 분포.
3. `recptnDt` 오류(과거·미래)가 얼마나 자주 나는가. 강일·천호처럼 늘 이상한 역은 어디인가.
4. 2~9호선에서 실측과 공식 시간표의 차이(지연)는 얼마인가. 작으면 시간표가 있는 노선에서는 모델 효과가 작다.
5. 위치 API에 나오는 노선과 나오지 않는 노선, 노선별 관측 열차 수와 하루 시간대별 결측.

## 4. 모델(단순한 것부터)

평가 기준은 모두 같다. **날짜로 나눈** 시험 세트(앞 날짜로 만들고 뒤 날짜로 평가)에서 예측 시각과 실측 시각의 차이를 본다. MAE(초), 90백분위(P90), ±60초·±120초 안에 든 비율. 요일 구분·호선별로도 나눠 보고한다.

| 단계 | 모델 | 쓰는 곳 |
|---|---|---|
| B0 | 공식 시간표 그대로(2~9호선, 서버 `TimetableService`와 같은 출처) | 기준선 |
| B1 | **실측 시간표**: (요일 구분, 호선, 방향, 역, `trainNo`)별 출발 시각의 중앙값. `trainNo`가 날마다 다르면 (요일 구분, 호선, 방향, 역)별로 하루 출발 시각을 모아 시간대별로 묶어 대표 시각 목록을 만든다. 관측 일수가 N일 미만인 칸은 내지 않는다 | 쓰임 1·3 |
| B2 | **구간 시간 추정**: 열차의 마지막 관측 위치·시각 + (요일 구분, 시간대, 구간)별 이동 시간·정차 시간 중앙값의 합 | 쓰임 2, 이상값 거르기 |
| M1 | **보정 모델**: LightGBM 회귀로 B1·B2의 오차를 예측해 더한다. 특징: 요일 구분, 시간대(분), 역 순서, 남은 정거장 수, 마지막 관측 뒤 지난 시간, 그날 그 호선의 최근 지연, 급행·막차 | B1·B2보다 확실히 나을 때만 |

- 학습은 오프라인 스크립트. 결과물(중앙값 표, 나중에 LightGBM 파일)은 `server/data/`에 두고 서버는 요청 때 읽기만 한다. 결과물에 버전·학습 기간·관측 수를 적는다.

## 5. 서버·앱 통합(계획만, 평가 숫자가 나온 뒤)

- `TimetableService` 옆에 `PredictionService`. 순서: 실시간 → 공식 시간표 → 예측 → 없음. 시간표가 없는 노선은 예측이 대신한다.
- 응답 `source`에 `"predicted"`. 앱은 "예측"으로 표시(시간표 기준과 구분).
- 관측 수가 하한 미만이거나 평가에서 그 칸이 B0보다 나쁘면 예측하지 않는다.
- 탄 열차 예측(쓰임 2)은 열차 번호 + B2로 별도 엔드포인트 또는 기존 경로 응답 확장 — 통합 단계에서 정한다.
- 주 1회 다시 학습. Render 무료 서버는 결과물 파일만 받는다(배포에 포함).
- M1(LightGBM)은 데이터 4주 이상, B1·B2 평가 뒤 선택.

## 6. 일의 순서

1. **수집기**(바로): 위치 API → `raw_snapshots`·`events`·`station_map`·`key_usage`, 키 전환·337 처리, 중복 제거, 백업, `docs/ml/collector.md`(VM 준비·`systemd`·백업·PC 대안으로 작업 스케줄러). 개발 PC에서 1시간 이상 돌려 관찰 결과를 `docs/ml/`에 기록(나온 노선, `trainSttus`·`recptnDt` 모양, 비서울 노선 여부).
2. **분석·모델 파이프라인**(지금 쓰고, 기록한 데이터로 테스트): 첫 주 분석 스크립트(§3), B1 빌더, B2 추정기, 평가 스크립트(B0 비교). 실제 학습은 데이터 1~2주 뒤.
3. **서버 통합·M1**: 평가 숫자가 나온 뒤. 이번에는 계획에만 둔다.

## 7. 위험

- 수집기가 서버 키를 쓰면 앱이 멈춘다 → 키 이름 허용 목록을 코드에 고정한다(§2.2).
- 실제 한도를 모른다 → 키별 호출 수 기록, 337이면 전환·정지.
- 위치 API 품질(누락 역, `recptnDt` 오류, 0시 30분 이후 소실) → 지우지 않고 표시, 관측 수 하한.
- 비서울 노선과 일부 노선은 위치 API에 없을 수 있다 → 첫날 확인 후 대상에서 뺀다.
- VM이 꺼지거나 디스크가 찬다 → `systemd` 재시작, 매일 백업, raw 보관 기간(구현자가 정함).

## 8. 개인 정보·보안

- 열차 공개 데이터만 모은다.
- 키는 사용자가 직접 `.env`에 넣는다. 구현자는 키 값을 출력·기록·커밋하지 않는다.

## 9. 정한 것(구현 계획이 따라야 할 것)

- 위치 API 하나만 쓴다(도착 API로 수집하지 않음).
- 30초 주기, 05:00~01:00 KST, 서울 노선 전부(첫날 확인 후 빈 노선 제외).
- 키 순서 위치 → 예비 1 → 예비 2, 실시간·일반 키 금지, 337이면 그날 그 키 정지.
- SQLite, 표 4개(§2.4), 중복 제거 키와 "가장 이른 `recptnDt`" 규칙, 01시 이전은 전날 서비스 날짜.
- 이상값은 표시만 하고 지우지 않는다.
