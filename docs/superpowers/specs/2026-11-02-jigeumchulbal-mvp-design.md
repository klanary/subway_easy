| 항목 | 내용 |
|---|---|
| 문서 상태 | 사용자 검토 대기 (승인 후 구현 계획 작성) |
| 작성일 | 2026-11-02 |
| 제출 마감 | 2026-11-26 (목표 제출일 2026-11-25) |
| 앱 이름 | 지금출발 (가칭, 변경 가능) |
| 저장소 이름 | `jigeumchulbal` |
| 패키지명 | `io.github.<GitHub 사용자명>.jigeumchulbal` |

이 문서는 구현 계획 작성과 Claude Code 개발의 기준 문서다. 이 문서와 다르게 구현해야 할 이유가 생기면 문서를 먼저 고친 뒤 구현한다.

---

## 1. 배경과 목표

### 1.1 목적
모바일앱개발협동조합 동계 현장실습(앱 개발·백엔드 분야) 지원용 포트폴리오를 만든다. 규모가 크더라도 **실제로 동작하고 시연할 수 있는 결과물**을 최우선으로 한다.

### 1.2 접근: 클론 + 개선
- 상용 대중교통 앱의 핵심 기능을 공개 API로 직접 구현하고, 지하철 통학 사용자 관점의 개선을 더한다. 비교 대상 앱은 카카오맵(길찾기)과 카카오지하철(역 실시간 정보)이다.
- 상용 앱 설치 파일의 디컴파일 같은 역공학은 하지 않는다.
- 원본 앱의 이름, 아이콘, 디자인 리소스는 사용하지 않는다.

### 1.3 하위 프로젝트 로드맵

| 차수 | 범위 | 시점 |
|---|---|---|
| 1차 (이 문서) | 지하철 실시간 도착, 길찾기·지도, 통학 세션 알림, 내 장소·즐겨찾기 | 2026-11-26 제출 |
| 2차 | 버스 실시간 도착 (서울 → 경기) | 제출 이후 |
| 3차 | 서버 푸시(FCM) 기반 알림, 하차 알림 실시간 보정 등 | 실습 기간 또는 이후 |

각 차수는 별도의 스펙 → 구현 계획 → 개발 주기를 가진다. 1차 구조는 2·3차를 수용할 수 있게 설계한다.
- 서버: 외부 API 연결 계층을 데이터 출처별로 분리한다.
- 앱: 알림 예약 모듈을 인터페이스 뒤에 둔다.

## 3. 범위

### 3.1 필수 기능

| 번호 | 기능 | 완료 조건 |
|---|---|---|
| ① | 역 실시간 도착 | 역 상세에서 호선·방향별 다음 열차 최대 2대의 남은 시간, 행선지, 막차·급행 여부를 표시한다. 화면이 보이는 동안 30초마다 갱신하고 "n초 전 갱신"을 표시한다. 역을 즐겨찾기(별표)하면 홈에 그 역의 실시간 도착이 표시된다. |
| ② | 통합 검색 + 내 장소 | 검색창 하나로 역(이름·초성)과 장소를 함께 검색한다. 내 장소(집·학교·회사·직접 추가)와 최근 검색(최대 20개)을 검색 화면에 함께 보여준다. 출발 칸의 기본값은 현재 위치이며, 위치 권한이 없으면 빈 칸으로 둔다. |
| ③ | 지도에서 지정 | 지도를 탭하거나 끌어서 가운데 고정 핀을 맞추면 주소와 가장 가까운 역을 보여주고, [출발] [경유] [도착] 버튼으로 지정한다. |
| ④ | 경로 결과와 지도 | 경로 카드 목록(총 소요 시간, 환승 횟수, 요금, 구간 막대)과, 선택한 경로를 구간별 색으로 지도에 그린 상세 화면을 제공한다. |
| ⑤ | 하차 알림 | 탑승 시점부터 경로의 구간별 소요 시간으로 각 하차·환승 지점의 도착 시각을 계산하고, 각 지점 2분 전(설정 가능)에 알린다. |
| ⑥ | 서버 기반 | 외부 API 키는 서버에만 둔다. 캐시, 호출 한도 보호, IP별 요청 제한을 적용하고 공개 URL로 배포한다. |
| ⑦ | 승차 전 알림 | 경로 상세에서 시작하면 도보 시간을 반영해 "지금 출발해야 탈 수 있는 시각"에 알린다(8.2절). 역 상세에서 시작하면 선택한 방향 열차의 도착 3분 전(설정 가능)에 알린다. |
| ⑧ | 경유지 | 경유지 1곳을 추가할 수 있고, 서버가 두 구간의 경로를 합성해 돌려준다(6.6절). |
| ⑨ | 자주 가는 경로 | 경로를 즐겨찾기하면 홈에 카드로 표시되고, 탭 한 번으로 경로 결과를 연다. 카드는 현재 시간대의 사용 빈도순으로 정렬한다(7.2절). |
| ⑩ | 실시간 결합 | 경로 카드마다 첫 지하철 탑승역의 해당 방향 다음 열차 정보를 붙인다(6.6절). |

### 3.2 여유 기능 (필수를 모두 마친 뒤 시간이 남을 때만)
- ⑪ 실시간 열차 정보로 하차 알림 시각 보정
- ⑫ 경로 결과의 "지하철만 보기" 필터

### 3.3 범위 밖
- 버스 실시간 도착 (2차)
- 회원가입·로그인
- 서버 푸시(FCM) 알림 (3차)
- iOS 앱, Play 스토어 출시
- 지하철 노선도 화면
- 다국어 지원
- 출발 시각을 미리 정해 경로 검색하기 (카카오 경로 API가 출발 시각 파라미터를 제공하지 않음)

### 3.4 일정 지연 시 최소 동작 버전
점검일(2026-11-15, 2026-11-20)까지 끝나지 않은 기능은 빼지 않고 아래의 최소 버전으로 완성한다. 최소 버전으로 바꾼 기능은 README의 "알려진 한계"에 적는다.

| 기능 | 정식 버전 | 최소 동작 버전 |
|---|---|---|
| ③ 지도에서 지정 | 핀 + 주소 + 가장 가까운 역 | 핀 좌표로 바로 지정 (주소 표시 생략) |
| ④ 경로 지도 | 구간별 색 + 출발·환승·도착 마커 | 단색 경로선 |
| ⑤ 하차 알림 | 하차·환승 지점마다 알림 | 최종 하차 지점만 알림 |
| ⑦ 승차 전 알림 | 출발 타이밍 (도보 시간 반영) | 역 상세의 "도착 N분 전" 알림만 |
| ⑧ 경유지 | 3×3 조합 중 상위 5개 | 구간별 최적 경로 1개씩 이어 붙이기 |
| ⑨ 자주 가는 경로 | 홈 카드 + 시간대별 정렬 | 홈 카드 목록 (최근 사용순) |
| ⑩ 실시간 결합 | 모든 경로 카드에 표시 | 선택한 경로의 상세 화면에서만 표시 |

## 4. 사용자 흐름과 화면

### 4.1 흐름

```
홈 ─(자주 가는 경로 카드 1탭)──────────────────> 경로 결과 ──> 경로 상세(지도) ──> 통학 세션
 ├─(검색창 / 내 장소 칩)──> 경로 편집 ─(칸 탭)─> 통합 검색 ─(지도에서 선택)─> 지도 핀 선택
 └─(즐겨찾는 역)──> 역 상세(실시간) ─(승차 전 알림)─> 통학 세션
```

### 4.2 화면 구성

| 화면 | 구성 | 간편함 포인트 |
|---|---|---|
| 홈 | 검색창, 내 장소 칩(집·학교·회사), 자주 가는 경로 카드, 즐겨찾는 역의 실시간 도착, 진행 중인 세션 배너 | 자주 가는 경로는 입력 없이 1탭으로 결과 확인 |
| 경로 편집 | 출발·도착 칸, "+ 경유지" 버튼(누를 때만 칸이 펼쳐짐), 출발↔도착 바꾸기, [검색] | 출발 기본값이 현재 위치 |
| 통합 검색 | 검색창 하나, 결과 구역(내 장소 / 최근 검색 / 역 / 장소), "지도에서 선택" 버튼 | 초성 검색(ㅎㄷㅇㄱ → 홍대입구), 검색 대상 구분 없이 입력 |
| 지도 핀 선택 | 가운데 고정 핀, 하단 카드(주소, 가장 가까운 역), [출발] [경유] [도착] | 버튼 하나로 지정 |
| 경로 결과 | 경로 카드 목록: 총 소요 시간, 환승 횟수, 요금, 구간 막대(도보·지하철·버스), 첫 탑승역 "다음 열차 N분" | 실시간 정보를 목록에서 바로 확인 |
| 경로 상세 | 위: 지도(구간별 색 경로, 출발·환승·도착 마커). 아래: 끌어 올리는 단계별 안내. 버튼: [승차 전 알림] [출발(하차 알림)] [★ 즐겨찾기] | 경로 확인부터 알림 시작까지 한 화면 |
| 역 상세 | 호선별 상행·하행(2호선은 내선·외선) 다음 열차 2대, 남은 시간, "n초 전 갱신", [★] [승차 전 알림] | 화면이 보일 때만 30초마다 자동 갱신 |
| 통학 세션 | 대기: "지금 출발하면 N분 뒤 열차 탑승 가능". 탑승: "OO까지 N정거장, 약 N분" 카운트다운. [탑승했어요] [종료] | 휴대폰 상단 알림에서도 확인·조작 |
| 설정 | 내 장소 관리, 알림 시점(8.6절 기본값), 권한 상태, 정보(데이터 출처 표시) | — |

### 4.3 출발 타이밍 알림 (⑦의 핵심)
- 경로 상세에서 승차 전 알림을 시작하면, 경로의 "첫 지하철 탑승 전까지 걸리는 시간"과 실시간 도착 정보를 결합해 "지금 출발해야 이 열차를 탈 수 있다"는 시각에 알린다.
- 첫 지하철 탑승 전에 버스 구간이 있으면 도착 시간을 예측할 수 없으므로, 역 상세와 같은 "도착 N분 전" 방식으로 대신한다.
- 계산 규칙은 8.2절에 정의한다.

### 4.4 권한 요청 시점
- **위치:** "현재 위치"를 처음 사용할 때 요청한다. 앱을 쓰는 동안만 허용으로 충분하다.
- **알림, 알람 및 리마인더:** 첫 통학 세션을 시작할 때 이유를 설명하는 화면을 보여준 뒤 요청한다.
- 앱을 처음 실행할 때 권한을 한꺼번에 요청하지 않는다.

### 4.5 공통 화면 상태
- 모든 데이터 화면은 로딩, 내용, 빈 결과, 오류(다시 시도 버튼), 오프라인의 다섯 가지 상태를 가진다.
- 서버 응답에 `stale: true`가 있으면 해당 정보를 흐리게 표시하고 "갱신 지연"을 붙인다.
- 지도 SDK 초기화에 실패해도 경로 목록과 단계별 안내는 정상 동작한다. 지도 영역에는 "지도를 불러오지 못했어요"를 표시한다.

### 4.6 원본 대비 측정 과제
| # | 과제 | 비교 대상 |
|---|---|---|
| T1 | 집에서 학교까지 경로 찾기 (앱 실행 직후부터 경로 목록이 보일 때까지) | 카카오맵 |
| T2 | 경유지 1곳을 넣어 경로 찾기 | 카카오맵 (경유지를 지원하지 않으면 같은 목적을 달성하는 조작 전체) |
| T3 | 특정 역의 특정 방향 다음 열차 확인 | 카카오지하철 |

- 측정 방법: 과제마다 3회씩 화면 녹화하고, 탭 수와 소요 시간의 중앙값을 기록한다.
- 원본 앱 측정은 구현 시작 전(1주차)에, 지금출발 측정은 4주차에 한다.
- 결과는 `docs/measurements/ux-comparison.md`에 정리한다.

## 5. 전체 아키텍처

### 5.1 저장소 구조

```
jigeumchulbal/
├─ android/                 안드로이드 앱 (Kotlin, Jetpack Compose)
├─ server/                  중계 서버 (Python, FastAPI)
├─ docs/
│  ├─ superpowers/specs/    설계 스펙 (이 문서)
│  ├─ superpowers/plans/    구현 계획
│  ├─ analysis/             원본 앱 분석
│  ├─ measurements/         UX 비교, 부하 테스트 결과
│  └─ learning/             학습 노트
├─ .github/
│  ├─ workflows/            CI (server.yml, android.yml)
│  └─ ISSUE_TEMPLATE/       버그 템플릿
└─ README.md
```

### 5.2 데이터 흐름

```
[안드로이드 앱] ──HTTPS/JSON──> [중계 서버] ──> 서울시 실시간 지하철 도착 API
   │                              │         ──> 카카오 키워드 장소 검색 / 좌표→주소 변환
   │                              │         ──> 카카오 대중교통 경로 조회
   │                              └─ 역 기준 데이터(SQLite, 읽기 전용) + 메모리 캐시
   └─ 카카오 지도 SDK (지도 표시와 핀 선택은 앱에서 직접 처리)
```

### 5.3 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 앱 언어·UI | Kotlin, Jetpack Compose (Material 3), Navigation Compose | 현재 안드로이드 표준 |
| 앱 상태 관리 | ViewModel + StateFlow | 화면 상태를 한곳에서 관리 |
| 앱 네트워크 | Retrofit, OkHttp, kotlinx.serialization | 표준적이고 자료가 많음 |
| 앱 저장 | Room (내 장소·즐겨찾기·최근 검색), DataStore (설정·진행 중 세션) | 구조화 데이터와 단순 설정을 분리 |
| 지도 | 카카오 지도 Android SDK v2 | 경로 API와 같은 카카오 체계, 국내 지도 품질 |
| 현재 위치 | Google Play 서비스 위치 API (FusedLocationProviderClient) | 배터리 효율적인 표준 방법 |
| 의존성 연결 | 직접 만든 컨테이너 클래스 (`AppContainer`) | 규모가 작고 구조가 그대로 보여 설명하기 쉬움 |
| 앱 SDK 수준 | minSdk 26, targetSdk·compileSdk는 구현 시점의 최신 안정 API 레벨(35 이상) | 알림 채널과 java.time을 기본으로 쓸 수 있음 |
| 서버 | Python 3.12, FastAPI, uvicorn, httpx(비동기), pydantic v2 | Python 강점 활용, API 문서 자동 생성 |
| 서버 저장 | SQLite 파일 (역 기준 데이터, 읽기 전용) | 무료 호스팅 DB의 만료 문제를 피하고 배포가 단순 |
| 서버 캐시 | 직접 구현한 유효 시간(TTL) 메모리 캐시 + 동시 요청 합치기 | 서버 한 대 규모라 Redis 불필요, 직접 구현해 설명 가능 |
| 서버 테스트 | pytest, pytest-asyncio, respx(httpx 응답 대체), ruff(코드 검사) | 외부 API 없이 테스트 가능 |
| 배포 | Docker, Render 무료 웹 서비스, GitHub Releases(APK) | 비용 0원, 다른 호스팅으로 옮기기 쉬움 |
| CI | GitHub Actions | PR마다 자동 검증 |

### 5.4 키와 개인정보 원칙
- 서버용 키(서울시 인증키, 카카오 REST 키)는 서버 환경 변수에만 둔다. 저장소에는 키가 없는 `server/.env.example`만 올린다.
- 앱에는 카카오 지도 SDK용 네이티브 앱 키만 들어간다. 이 키는 카카오 콘솔에 등록한 패키지명과 서명 키 해시로 사용처가 제한된다.
- 내 장소, 즐겨찾기, 최근 검색, 세션 정보는 휴대폰에만 저장한다. 로그인이 없고 서버에 개인정보를 저장하지 않는다.
- 서버 로그에는 위치 좌표를 소수점 3자리까지만 남긴다.

### 6.2 엔드포인트

모든 응답은 서버가 정한 형식이다. 앱은 서울시·카카오의 응답 형식을 알지 못한다. 아래 예시의 값은 형식 설명용이며 실제 데이터가 아니다.

좌표는 요청·응답 모두 **위도, 경도 순서**를 쓴다. 카카오 API는 `x=경도, y=위도`를 쓰므로 변환은 서버의 카카오 연결 모듈 안에서만 한다.

#### `GET /health`
- 용도: 서버 상태 확인과 서버 깨우기
- 응답: `{"status": "ok"}`

#### `GET /v1/stations/search?q={검색어}&limit={개수}`
- `limit` 기본 20, 최대 50
- 검색어가 모두 한글 자음(ㄱ~ㅎ)이면 초성 검색, 아니면 이름 검색 (6.5절)

```json
{
  "items": [
    {"id": "홍대입구", "name": "홍대입구", "lines": ["2호선", "경의중앙선", "공항철도"], "lat": 37.5571, "lng": 126.9245}
  ]
}
```

#### `GET /v1/stations/{id}/arrivals?line={호선}&towards={방면 역 이름}`
- `line`, `towards`는 선택 파라미터이며, 주면 해당 그룹만 돌려준다.
- `remainingSec`는 서버 응답 시점 기준 남은 초다. 앱은 응답을 받은 시각에 더해 도착 예정 시각으로 바꿔 쓴다.

```json
{
  "stationId": "홍대입구",
  "updatedAt": "2026-11-02T08:01:30+09:00",
  "stale": false,
  "groups": [
    {
      "line": "2호선",
      "direction": "내선",
      "towards": "합정",
      "trains": [
        {"destination": "성수", "remainingSec": 180, "message": "3분 후", "isLast": false, "isExpress": false},
        {"destination": "성수", "remainingSec": 420, "message": "7분 후", "isLast": false, "isExpress": false}

```

#### `GET /v1/places/search?q={검색어}&lat={위도}&lng={경도}`
- `lat`, `lng`는 선택이며, 주면 가까운 순으로 정렬한다. 결과는 최대 15개다.

```json
{
  "items": [
    {"name": "홍익대학교 서울캠퍼스", "address": "서울 마포구 ...", "lat": 37.5509, "lng": 126.9255, "category": "학교"}

```

#### `GET /v1/places/reverse?lat={위도}&lng={경도}`

```json
{
  "address": "서울 마포구 ...",
```

#### `GET /v1/routes?from={위도,경도}&to={위도,경도}&via={위도,경도}&fromName=&toName=&viaName=`
- `via`, 이름 파라미터는 선택이다. 결과는 최대 5개다.
- 경유지가 없으면 `legs`는 1개, 있으면 2개(출발→경유, 경유→도착)다.

```json

  "stale": false,

    {
      "id": "r_3f9a",
      "type": "SUBWAY",
      "totalSec": 1980,
      "distanceM": 11800,

      "fare": 1550,

             "stops": ["홍대입구", "합정", "당산"], "boardStationId": "홍대입구", "alightStationId": "당산",
             "guidance": "2호선 홍대입구 승차, 당산 하차", "path": [[37.5571, 126.9245], [37.5349, 126.9025]]}
```

- `step.mode`: `WALK`, `SUBWAY`, `BUS`

### 6.3 오류 응답

형식: `{"error": {"code": "...", "reason": "...", "message": "사용자에게 보여줄 문구"}}` (`reason`은 선택)

| HTTP | code | 발생 조건 |
|---|---|---|
| 400 | `INVALID_REQUEST` | 파라미터 형식 오류, 출발지와 도착지가 같음(카카오 `EQUAL_POINTS`) |
| 404 | `NOT_FOUND` | 없는 역 ID |
| 404 | `NO_ROUTE` | 카카오 `STARTNODES_NULL`(reason `NO_START_STOP`), `ENDNODES_NULL`(`NO_END_STOP`), `NO_RESULTS`(`NO_RESULTS`) |
| 429 | `RATE_LIMITED` | IP별 요청 제한 초과 |
| 502 | `UPSTREAM_ERROR` | 외부 API 오류 응답(카카오 `INVALID_REQUEST` 포함), 재시도 후에도 실패하고 만료된 캐시도 없음 |
| 503 | `QUOTA_EXCEEDED` | 외부 API 일일 한도 소진, 만료된 캐시도 없음 |
| 504 | `UPSTREAM_TIMEOUT` | 외부 API 시간 초과, 재시도 후에도 실패하고 만료된 캐시도 없음 |

- 외부 API 호출은 5초 제한을 두고, 실패하면 0.5초 뒤 1회 재시도한다.
- 실패했지만 유효 시간이 지난 캐시가 있으면 그 데이터를 `stale: true`로 돌려준다(200).

### 6.4 캐시와 호출 한도 보호

| 데이터 | 캐시 키 | 유효 시간 |
|---|---|---|
| 실시간 도착 | 역의 API 조회용 이름 (한 번 호출에 그 역의 모든 호선이 옴) | 20초 |
| 경로 | 출발·경유·도착 좌표를 소수점 4자리(약 10m)로 반올림한 값 | 10분 |
| 장소 검색 | 검색어 + 좌표(소수점 2자리 반올림) | 24시간 |
| 좌표→주소 | 좌표(소수점 4자리 반올림) | 24시간 |
| 역 검색 | 캐시 없음 (메모리 인덱스에서 바로 계산) | — |

- 경로 캐시에는 카카오 경로 결과만 저장한다. 실시간 정보(⑩)는 응답할 때마다 실시간 도착 캐시에서 새로 붙인다.
- **만료된 항목 보관:** 만료된 항목은 즉시 지우지 않고 최대 24시간 보관해 장애 시 `stale` 응답에 쓴다.
- **동시 요청 합치기:** 같은 캐시 키로 외부 호출이 진행 중이면, 뒤따른 요청은 새로 호출하지 않고 진행 중인 호출의 결과를 함께 기다린다.
- **호출 한도 보호:** 외부 API별 일일 호출 수를 센다. 한국 시간 00:00에 초기화한다.
  - 한도의 80% 이상: 해당 API 데이터의 캐시 유효 시간을 3배로 늘린다.
  - 한도 도달: 외부 호출을 멈추고, 캐시가 있으면 `stale: true`로, 없으면 `QUOTA_EXCEEDED`로 응답한다.
  - 외부 API가 한도 초과 응답(예: 카카오의 429)을 보내면 그날은 한도에 도달한 것으로 처리한다.
  - 카운터는 메모리에 있으므로 서버가 재시작되면 초기화된다. 이 한계는 위의 "한도 초과 응답 감지"로 보완한다.

### 6.5 역 기준 데이터와 이름 매칭

**데이터 생성**
- 원천: 서울시 역사마스터 정보(역사 ID, 역사명, 호선명, 좌표). 내려받은 원본은 `server/data/raw/`에 둔다.
- `server/scripts/build_stations.py`가 원본을 읽어 `server/data/stations.sqlite`를 만든다. 생성된 파일도 저장소에 커밋한다. 스크립트는 같은 입력이면 같은 결과를 낸다.

**테이블**

| 테이블 | 컬럼 |
|---|---|
| `stations` | `id`(정규화된 역 이름, 기본 키), `display_name`, `lat`, `lng`, `chosung`, `api_name`(실시간 API 조회용 이름) |
| `station_lines` | `station_id`, `line_name`(정규화된 호선 이름), `master_id`(원천 데이터의 역사 ID) |
| `aliases` | `alias`(기본 키), `station_id` |

- 같은 이름의 역은 호선이 달라도 `stations`의 한 행으로 묶는다. 서울시 실시간 API가 역 이름으로 조회하면 모든 호선 정보를 함께 돌려주기 때문이다.
- `lat`, `lng`는 같은 역에 속한 호선 좌표들의 평균이다.

**이름 정규화 규칙** (빌드 스크립트와 서버가 같은 함수를 쓴다)
1. 앞뒤 공백을 제거하고, 연속된 공백은 하나로 줄인다.
2. 끝의 "역"을 제거한다(예: "서울역" → "서울", "홍대입구역" → "홍대입구"). 제거 후 남는 글자가 1자 이하면 제거하지 않는다.
3. 괄호 안 이름은 별칭으로 분리한다. 예: "총신대입구(이수)" → `id` "총신대입구", 별칭 "이수"와 "총신대입구(이수)"

**실시간 API 이름 예외**
- 서울시 실시간 API는 일부 역을 특수한 이름으로 조회해야 한다. 예: "응암" → "응암순환(상선)", "공릉" → "공릉(서울산업대입구)".
- 이런 예외는 `stations.api_name`에 넣는다. 예외 목록은 1단계(14절)에서 서울시 데이터셋 안내 문구를 보고 채운다.

**호선 이름 정규화**
- "수도권 2호선", "서울 2호선", "2호선"처럼 출처마다 다른 표기를 하나("2호선")로 통일하는 매핑 표를 둔다.
- 카카오 경로 응답의 실제 호선 표기는 1단계에서 샘플로 확인해 표에 반영한다.

**검색 규칙**
- **초성 검색:** 검색어가 모두 한글 자음이면 `chosung` 컬럼에서 찾는다.
- **이름 검색:** 그 외에는 `id`와 별칭에서 찾는다.
- **정렬:** 완전 일치 > 앞부분 일치 > 포함 순으로 정렬하고, 같으면 호선 수가 많은 역, 그다음 이름순으로 정렬한다.

**매칭 실패 처리**
- 카카오 경로의 역 이름을 정규화한 뒤 `id`와 별칭에서 찾고, 실패하면 경고 로그(원본 이름 포함)를 남긴다.
- 실패 건수는 `/v1/metrics`의 `unmatchedStations`에 반영한다.
- 매칭 실패는 Issue로 등록하고 별칭을 추가해 해결한다. 이 기록이 실제 버그 수정 사례가 된다.

### 6.6 경로 처리

**카카오 호출**
- 카카오 `publictraffic`을 `start_x=경도, start_y=위도, end_x, end_y, s_name, e_name`으로 호출한다(좌표계 WGS84).

**단계 변환**
- 카카오 응답의 각 경로·단계를 6.2절 형식으로 바꾼다.
- 경로 좌표 `[x, y]`는 `[위도, 경도]`로 바꾼다.

**역 매칭**
- 지하철 단계마다 `stops`의 첫 역과 마지막 역을 매칭해 `boardStationId`, `alightStationId`를 채운다.

**첫 탑승 정보** (`firstBoarding`)
- 첫 번째 지하철 단계를 기준으로 만든다.
- `secToBoarding`: 그 단계 앞에 있는 모든 단계의 소요 시간 합
- `allWalkBeforeBoarding`: 앞 단계가 모두 도보인지 여부. 출발 타이밍 알림은 이 값이 `true`일 때만 쓴다.
- `towards`: 탑승역 바로 다음 역 이름(`stops[1]`의 정규화 이름). 정차역이 하나뿐이면 `null`이다.

**실시간 결합** (⑩)
- 결과 경로(최대 5개)의 서로 다른 탑승역마다 실시간 도착을 조회한다(캐시 사용).
- 각 역의 응답에서 `line`과 `towards`가 일치하는 그룹을 찾아, 그 그룹의 열차 최대 2대를 `nextTrains`에 넣는다.
- `towards` 비교는 양쪽 모두 정규화한 이름과 별칭으로 한다.

**경유지 합성** (⑧)
1. "출발→경유"와 "경유→도착"을 각각 조회한다(각각 캐시).
2. 각 결과의 소요 시간 상위 3개씩을 조합해 9개의 후보를 만든다.
3. 후보의 `totalSec`, `distanceM`, `fare`, `transfers`는 두 구간의 합으로 계산한다. 경유지에서 내리는 것은 환승으로 세지 않는다.
4. `totalSec` 오름차순, 같으면 `transfers` 오름차순으로 정렬해 상위 5개를 돌려준다.
5. `firstBoarding`은 첫 번째 구간 기준으로 만든다.

### 6.7 남은 시간 계산

서울시 실시간 응답의 한 열차 항목에서 `remainingSec`를 다음 순서로 정한다.
1. 도착 예정 초(`barvlDt`)가 0보다 크면: `barvlDt − (현재 시각 − 생성 시각 recptnDt)`. 생성 시각은 한국 시간으로 해석한다.
2. 그렇지 않으면 안내 문구(`arvlMsg2`)를 해석한다.

| 문구 패턴 | 추정 남은 초 |
|---|---|
| "N분 M초 후" | N×60 + M |
| "N분 후" | N×60 |
| "곧 도착" 또는 "진입" (전역 아님) | 30 |
| "도착" (전역 아님) | 0 |
| "전역 출발" | 90 |
| "전역 도착" | 120 |
| "전역 진입" | 150 |
| "[N]번째 전역" | N×120 |

3. 둘 다 해석할 수 없으면 `null`(앱에는 "정보 없음"으로 표시)이다.
4. 결과가 음수면 0으로 바꾼다.

- 추정 상수는 실측 로그로 보정한다. 보정 이력은 학습 노트에 남긴다.
- `message`에는 원본 안내 문구를 그대로 넣는다.
- 그 밖의 필드 처리:
  - `direction`: 상하행 필드(`updnLine`, 상행·하행·내선·외선)에서 가져온다.
  - `destination`, `towards`: "OO행 - XX방면" 형식의 `trainLineNm`에서 OO과 XX를 분리한다.
  - `isExpress`: 열차 종류 필드(`btrainSttus`)에서 판단한다.
  - `isLast`: 응답의 막차 표시에서 판단한다.
- 실제 필드명과 값의 형식은 1단계에서 샘플 응답으로 확정하고, 그 샘플을 테스트 데이터로 저장한다.

### 6.8 보안과 로깅
- **IP별 요청 제한:** 분당 60회, 메모리 슬라이딩 윈도우 방식이다. 호스팅의 프록시 뒤에 있으므로 `X-Forwarded-For`의 첫 번째 IP를 기준으로 한다.
- **로그:** JSON 형식이며, 요청 ID, 경로, 상태 코드, 처리 시간, 캐시 적중 여부를 남긴다.
- **키 노출 방지:** 서울시 API는 인증키가 URL 경로에 들어가므로, 외부 호출 URL을 로그에 남길 때 키 부분을 반드시 가린다. 카카오 키는 요청 헤더에 들어가므로 헤더는 로그에 남기지 않는다.

**자주 가는 경로 정렬 (⑨)**

- 같으면 전체 사용 횟수, 그다음 최근 사용순으로 정렬한다.

### 7.3 지도
- 카카오 지도 SDK v2는 View 기반이므로 Compose의 `AndroidView`로 감싼다. 생명주기(resume/pause)를 화면 생명주기에 연결한다.
- **경로 그리기:** 단계별 `path`를 선으로 그린다. 도보는 회색 점선, 지하철은 호선 색, 버스는 초록색이다. 호선 색 표는 앱 리소스로 관리한다. 출발·환승·도착에는 마커를 표시한다.
- **핀 선택 모드:** 카메라 이동이 멈추면 500ms 뒤에 `/v1/places/reverse`를 호출한다. 연속으로 움직이면 마지막 위치만 호출한다.
- 지도 초기화에 실패하면 4.5절에 따라 지도 영역만 대체 문구로 바꾼다.

### 7.4 현재 위치
- `FusedLocationProviderClient.getCurrentLocation`을 균형 정확도로 호출하고, 5초 안에 응답이 없으면 마지막으로 알려진 위치를 쓴다.
- 위치 권한이 거부되면 출발 칸을 비워 두고 검색을 안내한다.

### 7.5 앱 설정값
- 서버 주소와 카카오 네이티브 앱 키는 `android/local.properties`에서 읽어 `BuildConfig`로 넣는다. `local.properties`는 커밋하지 않는다.

## 8. 통학 세션 (알림)

### 8.1 상태와 전이

```
[없음] ─(승차 전 알림 시작)─> [대기] ─([탑승했어요])─> [탑승] ─(마지막 지점 알림 + 5분)─> [종료]
   └────────────(출발(하차 알림) 시작)──────────────────────↗
[대기] ─(최대 대기 시간 경과 또는 [종료])─> [종료]
[탑승] ─([종료])─> [종료]
```

| 이벤트 | 설명 |
|---|---|
| `StartWaiting` | 경로 상세(출발 타이밍 모드) 또는 역 상세(N분 전 모드)에서 승차 전 알림 시작 |
| `ArrivalsUpdated` | 대기 중 30초마다 받은 실시간 도착 정보 |
| `Boarded` | [탑승했어요] 버튼 (앱 화면 또는 알림 버튼) |
| `StartRiding` | 경로 상세의 [출발(하차 알림)] 버튼. 지금 탑승한 것으로 간주 |
| `AlarmFired` | 예약한 알람이 울림 |
| `Cancel` | [종료] 버튼 |
| `Timeout` | 대기 최대 시간(기본 30분) 경과 |

- 세션은 한 번에 하나만 진행한다. 진행 중에 새 세션을 시작하면 기존 세션을 끝낼지 확인한다.
- 역 상세에서 시작한 대기 세션은 경로 정보가 없으므로, [탑승했어요]를 누르면 하차 알림 없이 종료한다.

### 8.2 대기 단계 (⑦ 승차 전 알림)
- **실행:** 포그라운드 서비스(`WaitingService`, 유형 `dataSync`)가 진행 중 알림을 띄운 채 30초마다 `/v1/stations/{id}/arrivals?line=&towards=`를 호출한다.
- **출발 타이밍 모드** (경로 상세에서 시작, `allWalkBeforeBoarding == true`)
  - `이동 시간` = `secToBoarding`, `여유 시간` = 설정값(기본 60초)
  - **탈 수 있는 열차:** `remainingSec ≥ 이동 시간 + 여유 시간`인 첫 열차
  - **출발 시각** = 응답 수신 시각 + 그 열차의 `remainingSec` − 이동 시간 − 여유 시간
  - 출발 시각에 알람을 예약하고, 조회할 때마다 다시 계산해 예약을 갱신한다. 네트워크가 끊겨도 마지막 예측대로 알림이 울린다.
  - 알람이 울리면 "지금 출발하세요: N분 뒤 OO행 열차" 알림을 보낸다.
  - 출발 시각을 60초 넘게 지났는데 [탑승했어요]가 없으면, 다음 탈 수 있는 열차로 다시 계산하고 "다음 열차 기준으로 다시 안내할게요" 알림을 한 번 보낸다.
- **N분 전 모드** (역 상세에서 시작, 또는 첫 탑승 전에 버스 구간이 있는 경로)
  - 선택한 방향의 첫 열차가 `remainingSec ≤ 설정값(기본 180초)`이 되는 시각에 알린다. 예약 갱신 방식은 위와 같다.
- **진행 중 알림 문구:** "홍대입구 2호선 합정 방면 · 다음 열차 4분 · 7분 뒤 출발"처럼 표시하고, 조회할 때마다 갱신한다.
- **종료 조건:** [탑승했어요](경로에서 시작한 세션은 탑승 단계로 전환, 역 상세에서 시작한 세션은 종료), [종료], 최대 대기 시간 경과. 대기 단계가 끝나면 포그라운드 서비스를 멈춘다.
- **조회 실패:** 실패한 조회는 무시하고 마지막 예측을 유지한다. 3회 연속 실패하면 진행 중 알림에 "실시간 정보 연결 끊김"을 표시한다.

### 8.3 탑승 단계 (⑤ 하차 알림)
- **포그라운드 서비스를 쓰지 않는다.**
- **하차 지점 목록:** 탑승 시각부터 경로 단계의 소요 시간을 차례로 더해 각 지하철·버스 단계의 하차 시각을 계산한다. 마지막 단계의 하차 지점이 최종 하차 지점이고, 나머지는 환승 지점이다. 경유지가 있으면 경유지 하차도 지점으로 포함한다.
- **탑승 기준 단계:**
  - 대기 단계에서 넘어온 경우: 첫 지하철 단계부터 계산한다.
  - [출발(하차 알림)]으로 바로 시작한 경우: 첫 번째 지하철·버스 단계부터 계산하고, 그 앞의 도보 단계는 제외한다.
- **알람:** 각 지점의 "하차 시각 − 설정값(기본 120초)"에 알람을 예약한다.
- **진행 중 알림:** 시스템 카운트다운(`setUsesChronometer` + `setChronometerCountDown`)으로 다음 지점까지 남은 시간을 표시한다. 앱이 꺼져 있어도 시스템이 갱신한다.
- 알람이 울리면 "곧 OO역이에요. 내릴 준비를 하세요" 같은 높은 중요도 알림을 진동과 함께 보내고, 진행 중 알림을 다음 지점으로 갱신한다.
- 마지막 지점 알림 5분 뒤 세션을 종료하고 진행 중 알림을 지운다.

### 8.4 알람 예약 (`AlarmScheduler`)
- **정확한 알람 권한이 있을 때** (`canScheduleExactAlarms() == true`): `setAlarmClock`으로 예약한다. 이 방식은 절전 모드에서도 제시간에 울린다.
- **권한이 없을 때:** `setAndAllowWhileIdle`(부정확)로 예약하고, 세션 화면과 진행 중 알림에 "알림이 늦을 수 있어요"를 표시한다.
- 알람마다 고유한 요청 코드를 쓴다. 세션이 바뀌거나 종료되면 이전 알람을 모두 취소한다.
- 3차(서버 푸시)로 확장할 때 바꿀 수 있도록 `AlarmScheduler`는 인터페이스로 정의한다.

### 8.5 알림 채널과 버튼

| 채널 | 중요도 | 용도 |
|---|---|---|
| `session_ongoing` | 낮음 (소리 없음) | 대기·탑승 진행 중 알림 |

- 대기 단계의 진행 중 알림 버튼: [탑승했어요] [종료]
- 탑승 단계의 진행 중 알림 버튼: [종료]
- 알림을 누르면 앱의 통학 세션 화면이 열린다.

### 8.6 권한, 설정 기본값, 대체 동작

**매니페스트 권한:** `INTERNET`, `ACCESS_COARSE_LOCATION`, `ACCESS_FINE_LOCATION`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_DATA_SYNC`, `SCHEDULE_EXACT_ALARM`, `RECEIVE_BOOT_COMPLETED`

**런타임 요청 순서** (첫 세션 시작 시)
1. 알림 권한
2. "알람 및 리마인더" 설정 화면 이동 안내

**거부 시 동작**
- 알림 권한 거부: 세션을 시작하지 않고, 앱 안에서만 진행 상황을 보여준다.
- 정확한 알람 거부: 8.4절의 부정확 알람으로 동작한다.

**설정 기본값**

| 항목 | 기본값 |
|---|---|
| 출발 여유 시간 | 60초 |
| 하차·환승 알림 시점 | 120초 전 |
| 역 상세 승차 전 알림 시점 | 180초 전 |
| 최대 대기 시간 | 30분 |

### 8.7 복원
- 세션 상태는 바뀔 때마다 DataStore에 저장한다.
- **앱 시작 시:** 저장된 세션을 불러온다. 대기 단계면 포그라운드 서비스를 다시 시작하고, 탑승 단계면 아직 지나지 않은 지점의 알람을 다시 예약한다.
- **재부팅 시(`BOOT_COMPLETED`):** 탑승 단계는 남은 지점의 알람을 다시 예약한다. 대기 단계는 부팅 직후 포그라운드 서비스 재시작 제약을 피하기 위해 다시 시작하지 않는다. 세션을 종료하고 "대기 알림이 중단됐어요" 알림만 보낸다.
- **정확한 알람 권한이 새로 허용되면**(`ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`): 진행 중 세션의 알람을 정확한 방식으로 다시 예약한다.

### 9.1 서버

| 통합 | pytest + respx (외부 API 응답을 `tests/fixtures/`의 실제 샘플로 대체) | 모든 엔드포인트의 정상·오류 흐름, 카카오 상태 코드별 오류 변환, `stale` 응답 |

### 9.2 앱

### 9.3 부하 테스트 (S3)
- `server/scripts/load_test.py`는 비동기 HTTP 클라이언트로 가상 사용자 N명(기본 50명)이 10분 동안 아래 시나리오를 반복하게 한다.
  - 정해진 역 3곳의 실시간 도착 조회 (30초 간격)
  - 정해진 경로 2개 검색 (2분 간격)
- 실행 전후의 `/v1/metrics`를 비교해 "앱 요청 수", "외부 API 호출 수", "캐시 적중률"을 계산한다.
- 결과는 `docs/measurements/load-test-YYYYMMDD.md`로 저장한다.
- 테스트는 배포 서버가 아닌 로컬 서버에서 한다. 외부 API 한도를 보호하기 위해 `MOCK_UPSTREAM=true`로 실행한다. 이 모드에서는 외부 연결 모듈(`clients`)이 `tests/fixtures/`의 샘플을 돌려주는 모의 클라이언트로 바뀌며, 모의 클라이언트도 호출 횟수를 `/v1/metrics`에 똑같이 기록한다.

## 10. 배포와 운영

### 10.1 서버
- `server/Dockerfile`: python:3.12-slim 기반, `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
- **배포:** Render 무료 웹 서비스(Docker)로 배포한다. 환경 변수는 Render 대시보드에서 설정하고, 헬스 체크 경로는 `/health`로 한다.
- **잠듦 대응** (Render 무료는 15분 동안 요청이 없으면 잠들고, 깨어나는 데 약 1분이 걸린다)
  1. 앱을 열면 `/health`를 먼저 호출하고, 기기에 저장된 내 장소·자주 가는 경로부터 화면에 보여준다.
  2. 평일 06:30~09:30, 17:00~20:00(한국 시간)에 무료 예약 호출 서비스로 10분마다 `/health`를 호출한다. 공식 지원 방식이 아니므로, 문제가 생기면 10.3절의 이전 경로를 쓴다.
- **환경 변수:**
  - 키: `SEOUL_REALTIME_API_KEY`, `KAKAO_REST_API_KEY`
  - 일일 한도: `SEOUL_REALTIME_DAILY_LIMIT`, `KAKAO_ROUTE_DAILY_LIMIT`, `KAKAO_KEYWORD_DAILY_LIMIT`, `KAKAO_COORD2ADDRESS_DAILY_LIMIT`
  - 기타: `RATE_LIMIT_PER_MINUTE`, `MOCK_UPSTREAM`(부하 테스트용)

### 10.2 앱
- **서명:** 릴리스 서명 키스토어는 로컬에만 두고 커밋하지 않는다. 별도 위치에 백업한다.
- **배포:** 버전 태그(`v0.1.0` 등)마다 GitHub Releases에 서명된 APK와 변경 내역을 올린다.
- **카카오 콘솔:** 패키지명과 디버그·릴리스 서명 키 해시를 모두 등록한다.
- **README 설치 안내:** "출처를 알 수 없는 앱 설치 허용" 방법을 포함한다.

### 10.3 이전 경로
같은 Docker 이미지를 다른 무료 호스팅(예: Oracle 상시 무료 VM)에 그대로 배포할 수 있게 유지한다. 서버는 상태를 저장하지 않으므로 이전할 때 옮길 데이터가 없다.

### 10.4 데이터 출처 표시
README와 앱의 설정 > 정보 화면에 서울 열린데이터광장과 카카오를 출처로 표시한다. 각 데이터의 이용허락 조건에 따른 문구를 쓴다.

## 12. 작업 방식 (Claude Code 연계)
- 구현 계획(`docs/superpowers/plans/`)은 작은 작업으로 나누고, 작업마다 "실패하는 테스트 → 구현 → 테스트 통과 → 커밋" 순서로 진행한다.
- 기능 단위로 브랜치와 PR을 만들고, 본인이 PR 내용을 읽은 뒤 머지한다.
- **학습 노트:** 작업이 끝날 때마다 `docs/learning/NN-주제.md`를 남긴다. Claude Code가 초안을 쓰더라도 본인이 직접 고쳐 쓴다.

```markdown
# NN. 주제
- 무엇을 만들었나:
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
- 막혔던 점과 해결:
- 예상 면접 질문과 내 답:
```

- **버그 기록:** 발견 즉시 `.github/ISSUE_TEMPLATE/bug.md`(재현 방법, 기대 결과, 실제 결과, 원인, 해결) 형식의 Issue를 만들고, 수정 PR에서 Issue를 닫는다.
- **원본 앱 분석:** `docs/analysis/original-app.md`에 원본 앱의 화면 흐름과 불편 사항을 기록한다.

## 14. 1단계 확인 항목 (11/2~11/3)

구현을 시작하기 전에 아래를 모두 확인하고, 결과를 `docs/analysis/api-verification.md`에 기록한다. 확인 결과가 이 문서와 다르면 문서를 먼저 고친다.

1. **서울시 실시간 도착 API**
   - 실시간 지하철 인증키를 발급받는다.
   - 역 3곳 이상(2호선 역, 환승역, 이름 예외 역 1곳 포함)의 실제 응답을 `server/tests/fixtures/`에 저장한다.
   - 6.7절에 쓴 필드(`barvlDt`, `recptnDt`, `arvlMsg2`, `trainLineNm`, `updnLine`, `btrainSttus`, 막차 표시)의 실제 이름과 값 형식을 확인한다.
2. **서울시 역사마스터 정보**
   - 원본 파일을 내려받아 컬럼 이름과 좌표 형식을 확인한다.
   - 실시간 API 이름 예외 목록을 데이터셋 안내 문구에서 수집한다.
3. **카카오**
   - 이 프로젝트용 앱을 만들고 카카오맵 API를 활성화한 뒤, 무료 쿼터 적용 여부를 확인한다.
   - 대중교통 경로 응답 샘플 3개 이상(지하철만, 버스+지하철, 환승 포함)을 저장하고, 지하철 단계의 호선 이름 표기를 확인한다.
   - 키워드 검색과 좌표→주소 응답 샘플을 저장하고, 좌표→주소의 실제 일일 쿼터를 확인해 6.1절 설정값을 고친다.
4. **카카오 지도 SDK 실험**
   - 빈 안드로이드 프로젝트에서 지도를 띄우고, 저장한 경로 샘플의 좌표로 선 1개를 그린다(디버그 키 해시 등록 포함).
5. **Render 배포 실험**
   - `/health`만 있는 최소 서버를 Docker로 배포해 공개 URL과 잠듦·깨어남 시간을 확인한다.
6. **GitHub**
   - 저장소를 만들고 GitHub 사용자명을 확정해 패키지명을 결정한다.
