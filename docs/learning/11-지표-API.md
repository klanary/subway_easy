# 11. 운영 지표 API

- 무엇을 만들었나: `GET /v1/metrics` — 서버 시작 시각, `/v1/` 요청 수와 요청 제한 횟수, 캐시 적중·실패와 적중률, 외부 API별 오늘 호출 수·한도·오류 수, 매칭에 실패한 역 이름 수(스펙 6.2).
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 성공 기준 S3("앱 요청 수 대비 외부 API 실제 호출 수")를 숫자로 보여주려면 서버가 직접 세야 한다. 부하 테스트 전후로 이 API를 불러 차이를 계산한다(P2 Task 15).
  - 응답 모델을 pydantic으로 정의해 `/docs`에 형식이 그대로 드러나고, 파이썬의 snake_case 필드가 JSON에서는 camelCase로 나간다(`ApiModel`).
  - `/v1/metrics` 자신의 호출은 요청 수에 넣지 않는다. 부하 테스트가 측정하려고 부르는 호출이 결과를 흔들지 않게 하기 위해서다.
  - 요청이 하나도 없는 서버에서도 적중률이 0으로 나누기 오류 없이 0.0이다(부하 테스트가 맨 먼저 부르는 상황).
- 막혔던 점과 해결:
  - 계획의 두 번째 테스트(조회 2번 뒤 적중 1·실패 1)는 실시간 도착 API(P2 Task 9)가 있어야 한다. 지금은 카운터를 직접 바꿔 응답 형식을 확인하는 테스트로 대신하고, 원래 테스트는 Task 9 이후에 켜도록 건너뛰기로 남겼다.
- 예상 면접 질문과 내 답:
  - Q. 지표를 Prometheus 같은 도구로 내보내지 않은 이유는? A. 1차는 서버 한 대, 무료 호스팅이라 별도 수집 서버를 둘 수 없다. 부하 테스트 보고서에 필요한 숫자만 JSON으로 내보내는 것으로 충분했다. 확장한다면 같은 카운터를 Prometheus 형식으로도 내보내면 된다.
  - Q. 서버가 재시작되면? A. 지표는 메모리에 있어 0으로 돌아간다. 응답의 `since`로 언제부터 센 값인지 알 수 있다.
