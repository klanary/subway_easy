# 시간표 변경 감지와 실측 시간표(B1) 갱신 — 운영 안내

계획은 `docs/superpowers/plans/2026-11-16-timetable-change-handling.md`, 코드는 `server/ml/`(`points.py`, `changes.py`, `nightly.py`, `b1.py`, `b0.py`)에 있다. 수집기 운영은 `docs/ml/collector.md`를 본다.

> **지금 상태(2026-11-17):** VM(`subway-collector`)에 타이머를 켰다(매일 02:40, 관찰 모드). 같은 날 08:36에 손으로 한 번 돌려 확인했다: 14초(CPU 11초), 종료 코드 0, 하루치(11-16)를 뽑았고 날짜가 하루뿐이라 칸 0개·의심 0건이었다. 그동안 수집기는 멈추지 않았다. **기준값은 실제 자료로 맞추지 않은 초안**이라 밤 작업은 **관찰 모드**로 돈다(변경을 기록만 하고 B1에는 적용하지 않음). 평일 시간표는 3일치가 쌓여야 생기므로 2026-11-18 밤 전에는 판단할 것이 없다. 토요일은 12-05, 일요일은 12-06부터다.

## 1. 무엇이 일어나나

매일 02:40(백업 02:10 뒤, 수집 시작 05:00 전)에 `python -m ml.nightly`가 돈다.

1. 전날 하루치 이벤트를 호선 하나씩 읽어 "역마다 출발 시각 하나"로 줄여 `ml_data/points.sqlite`에 넣는다. 시간대별 정상 응답 수도 함께 적는다.
2. 호선·방향·1시간대 단위로, 전날 관측을 그 전날까지의 실측 시간표와 견줘 변경을 판단한다. 결과는 `ml_data/change_state.json`(상태)과 `ml_data/changes.md`(사람이 읽는 기록)에 남는다.
3. 실측 시간표를 다시 만들어 `ml_data/artifacts/measured_timetable.json`에 쓴다(바꾸기 전 것은 `.prev`).

VM이 며칠 꺼졌다 켜지면 빠진 날을 14일까지 날짜순으로 따라잡는다. 같은 밤에 다시 돌려도 결과가 같다.

## 2. 신호와 기준값(초안)

| 신호 | 뜻 | 기준 | 쓰는 노선 |
|---|---|---|---|
| `shifted` 어긋남 | 같은 열차 번호끼리 120초 넘게 어긋난 비율 | 30% 이상 | 번호가 날마다 같은 노선 |
| `numbers` 번호 | 사라지거나 새로 생긴 번호의 비율 | 20% 이상 | 번호가 날마다 같은 노선 |
| `moved` 짝 없음 | 번호를 보지 않고 시각만 120초 안에서 짝지었을 때 짝 없는 비율 | 30% 이상 | 전부 |
| `tph` 배차 | 시간당 출발 수의 변화 | ±20% 이상이고 역당 2대 이상 차이 | 전부 |
| `express` 급행 비율 | 급행 비율의 차 | ±0.15 이상 | 전부 |

- 기준 쪽 출발이 20건 미만인 단위, 그 시간대의 정상 응답이 96회(기대 120회의 80%) 미만인 날은 판단하지 않는다.
- 종류: 배차가 걸리면 `frequency`, 급행 비율이면 `pattern`, 번호만 바뀌고 시각은 그대로면 `renumber`, 그 밖은 `retime`.
- 2호선처럼 열차 번호가 날마다 다른 노선은 번호 신호를 쓰지 못하고, 배차 간격만큼 밀린 변화는 시각 짝짓기로도 보이지 않는다. 사실상 배차·급행 비율만 작동한다.

## 3. 의심 → 확정

| 다음 날(같은 요일 구분) | 결과 |
|---|---|
| 신호가 넘지 않음 | 해제(하루짜리 사고·지연으로 봄) |
| 신호가 넘고, 첫 의심일과 서로 맞음 | **확정**, 변경일 = 첫 의심일 |
| 신호가 넘지만 서로 맞지 않음 | 의심 유지. 3일 연속이면 확정 |
| 수집이 비어 판단 못 함 | 그대로. 네 번 못 보면 해제 |

- 공식 시간표를 다시 받아(§6) 그 단위가 바뀐 것으로 나와 있으면 의심 하루 만에 확정한다.
- 토요일·휴일은 다음 같은 요일 구분이 일주일 뒤라 확정도 일주일 걸린다.

## 4. 실측 시간표를 지키는 세 겹

1. **최근 창**: 평일 20일, 토요일 8일, 휴일 8일만 쓴다. 항상 적용.
2. **안 보인 열차 빼기**: 그 단위에 수집이 정상이었던 최근 날짜에 평일 3일(토·휴일 2일) 연속 안 보인 열차를 뺀다. 항상 적용. 감지가 놓쳐도 없어진 열차는 이 기간 뒤 사라진다.
3. **변경 기준일**: 확정된 단위는 변경일 이후 날짜만 쓴다(관측 일수 하한 2일). 이틀이 안 되면 그 단위는 `retraining`이고 시각을 내지 않는다. **`--enforce`일 때만 적용.**

결과물의 `scopes`에 `suspect`(의심), `retraining`(다시 배우는 중), `changed`(확정 뒤 14일)인 단위가 적힌다. 없는 단위는 정상이다. `changes`에는 최근 60일의 확정 기록이 있다.

## 5. 기록 읽기와 손으로 고치기

```bash
cd ~/subway_easy/server
cat ml_data/changes.md
.venv/bin/python -m ml.changes show
journalctl -u subway-ml-nightly -n 20
```

`changes.md`의 한 줄:

```
- 2026-11-23 확정 | 9호선 하행 평일 05~07시 | pattern | 급행 비율 +0.17, 번호 42% | 2026-11-20부터 | measured
```

날짜, 상태, 어디(호선·방향·요일 구분·시간대), 종류, 넘은 신호, 변경일, 근거(`measured` 실측, `official` 공식 시간표, `manual` 손으로) 순서다. 줄 끝에 `공식 시간표가 아직 옛것`이 붙으면, 실측은 바뀌었는데 공식 시간표 API가 아직 갱신되지 않은 것이다.

공지나 기사를 보고 손으로 확정하거나, 잘못된 확정을 되돌린다(방향은 0 상행·내선, 1 하행·외선. 요일 구분은 1 평일, 2 토요일, 3 휴일).

```bash
.venv/bin/python -m ml.changes mark --line 9호선 --direction 1 --day-type 1 --from 5 --to 7 --date 2026-11-20 --note "기사: 급행 증편"
.venv/bin/python -m ml.changes clear --line 9호선 --direction 1 --day-type 1 --from 5 --to 7 --note "폭설 때문이었음"
```

`clear`하면 그 단위는 다시 최근 창 전체를 쓴다. 다음 밤 작업부터 반영된다.

## 6. 공식 시간표 다시 받기(2~9호선, 주 1회)

```bash
python -m ml.b0 --refresh
```

- 전부 새로 받아 지난 캐시와 견주고, 달라진 단위를 `ml_data/official_diff.json`에 쓴다. 지난 캐시는 `timetable_cache-YYYYMMDD`로 최근 4개만 남는다. 하나라도 실패하면 아무것도 바꾸지 않는다.
- 밤 작업은 이 파일이 8일 안의 것이면 읽어, 10% 이상 달라진 단위의 의심을 하루 만에 확정한다. `ml_data/timetable_cache` 폴더가 있으면 확정 3일 뒤부터 공식 시간표가 따라왔는지도 본다.
- **일반 인증키(`SEOUL_OPENAPI_KEY`)가 필요하다.** VM `.env`에는 수집기 키만 있으므로 지금은 개발 PC에서만 돌릴 수 있다(그러면 결과 파일이 VM에 없어 밤 작업은 실측만으로 판단한다). VM에서 돌리려면 그 키를 VM `.env`에 더해야 하고, 주 약 1,800회 호출이 수집기와 같은 한도를 나눠 쓴다. 어느 쪽으로 할지는 아직 정하지 않았다.

## 7. 관찰 모드에서 적용 모드로

1. 자료가 평일 15일 이상 쌓이면(2026-12-07 이후) 기준값을 실제 지연 분포로 맞춘다(계획 Task 9: 정상인 날 의심 비율, 심어 본 변경을 며칠 만에 잡는지).
2. 기준값을 고친 뒤 VM 서비스에 `--enforce`를 더한다.

```bash
sudo sed -i 's|-m ml.nightly$|-m ml.nightly --enforce|' /etc/systemd/system/subway-ml-nightly.service
sudo systemctl daemon-reload
```

되돌리려면 `--enforce`를 지우면 된다. 관찰 모드에서도 1·2번 겹(최근 창, 안 보인 열차 빼기)은 항상 적용된다.

## 8. 알아 둘 것

- 결과물은 `server/ml_data/artifacts/`에 쌓일 뿐, 서버(앱)는 아직 읽지 않는다. 서버 통합은 별도 작업이다.
- `points.sqlite`는 하루 약 27MB이고 70일치를 둔다(약 2GB). 출발 시각은 수집 DB에서 다시 만들 수 있지만, 수집 횟수는 raw 응답이 지워지는 14일 뒤에는 다시 만들 수 없다. 이 파일을 지우면 그보다 오래된 날은 "수집 횟수 모름"이 되어 판단에서 빠진다.
- 상태 파일이 깨지면 밤 작업은 종료 코드 2로 멈추고 아무것도 쓰지 않는다. `change_state.json.prev`를 되돌려 놓고 다시 돌린다.
- 한 호선의 계산이 실패하면 그 호선은 이전 결과물의 시각을 그대로 두고 종료 코드 1로 끝난다(`journalctl`에 호선과 오류 종류가 남는다).
- 번호는 같고 시각만 120초 이하로 바뀐 변경은 잡지 못한다. 최근 창의 중앙값이 약 10평일에 걸쳐 따라간다.
- 실제 하루치(2026-11-16, 이벤트 43만 건)로 개발 PC에서 8.9초, 메모리 최대 142MB였다. VM 서비스에는 `MemoryMax=500M`을 걸어 두었다.
