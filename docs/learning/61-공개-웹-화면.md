# 61. A public web screen (for the use-case application)

- **What I built:** The server's first page (`/`) is now a web screen. You search for a station by name and see the next trains for each line and direction. It also serves the logo (`/logo.png`). The page is one HTML file (`server/app/web/index.html`) and uses only plain JavaScript. Through the existing `/v1/stations/search` and `/v1/stations/{id}/arrivals` it shows "N분 · X행 · 막차/급행" and refreshes every 20 seconds. Adding `?station=시청` opens that station directly.
- **Why I did it this way:**
  - The Seoul Open Data Plaza use-case application rejects localhost, GitHub and Notion links. It wants the URL of a web page or app that actually runs.
  - Options I considered:
    - A static page that only introduces the app. This is the quickest, but it might not count as "running".
    - A separate front-end hosting service. This means another deployment and another domain.
  - I picked the web screen on the same server because it adds no extra cost or deployment, and a reviewer can try it straight away.
  - The page and the API share one origin, so CORS is not needed.
  - The images were rendered and captured with Edge headless (`--screenshot`, `--virtual-time-budget`). This avoided adding Pillow or a browser automation tool.
- **Where I got stuck and how I fixed it:**
  - Korean time formatting showed "오전 12:53", so I used `hourCycle: "h23"`.
  - When the realtime source is the default, `source` is left out of the response, so the page treats a missing value as `realtime`.
- **Likely interview question and my answer:**
  - Q. Why not a separate front-end framework?
  - A. One screen and two API calls are enough. A build step and a second deployment would cost more than they give. Escaping the HTML is the only thing that needs care, and I handled it with the `esc()` function.
