# 열차 위치로 이 역 도착 시각 계산하기(설계)

2026-11-22, 수동 검토 중 합의. 구현 브랜치는 `polish3/manual-review`에서 이어 간다.

## 1. 왜

사용자는 **지금 있는 역에서 열차가 정확히 언제 오는지**를 보려 한다. 지금 앱은 두 군데에서 정확하지 않다.

- **[지금]의 코레일 원천 노선**(1호선, 4호선 코레일 구간, 경의중앙선, 공항철도, 경춘선, 수인분당선 등): 서울시 도착 API의 `barvlDt`(남은 초)가 거의 다 0으로 온다(2026-11-22 확인, 1호선 68행 중 67행). 서버는 `arvlMsg2` 문구("[5]번째 전역")를 읽어 **한 역 120초**로 어림한다(`server/app/services/remaining_time.py`). 역 간격이 긴 구간에서 많이 틀린다.
- **[시각 선택]**: 고른 시각이 가까워도 늘 시간표(공식·실측)만 쓴다. 지금 늦어지고 있는 운행이 반영되지 않는다.

## 2. 무엇을

열차의 **현재 위치**(서울시 실시간 위치 API `realtimePosition`)에서 이 역까지 **역 사이 실측 시간**(VM이 만든 B2 구간 시간)을 더해 도착 시각을 계산한다(사용자가 고른 방식 A).

- 열차 번호로 시간표와 짝짓지 않는다. 위치·방향·행선지·급행 여부만 쓴다.
- 지금까지 쌓인 지연은 위치에 이미 들어 있다. 반영하지 못하는 것은 앞으로 생길 지연과 시간표상 일부러 서 있는 시간뿐이다.
- 근거 자료: VM 수집 데이터로 잰 B2는 MAE 약 20초, ±60초 94%였다. 같은 관측의 공식 시간표(B0)와 견주면 2호선 9.7초 대 25.4초다(`docs/ml/2026-11-15-first-run-observations.md`).

## 3. 목표·비목표·반목표

**목표**

1. **[지금]**: 도착 API 열차의 `barvlDt`가 0(또는 없음)이면 그 열차의 위치로 계산한 남은 시간을 쓴다. `barvlDt`가 0보다 크면(서울교통공사 노선 등) 지금처럼 그 값을 쓴다. 위치로 계산하지 못하면 지금의 문구 어림을 쓴다.
2. **[시각 선택]**: 고른 시각이 지금부터 **60분 안**이면, 선로 위 열차들로 계산한 도착 시각 가운데 고른 시각 이후 열차를 보여 준다. 모자라면 시간표로 채운다. 60분 넘게 뒤면 지금처럼 시간표만.
3. **열차마다 근거 표시**: 실시간(도착 API 값) / 위치 계산 / 시간표 / 실측 시간표를 열차 줄마다 구분한다.

**비목표**

- 시간표 열차 번호와 짝짓기(방식 B), 지연 전파, 기계학습 보정(M1).
- 노선 지도에 열차 마커 그리기.
- 출근길 진행 화면(세션)의 계산 방식 바꾸기. 나중에 같은 계산을 쓸 수 있게 서버 쪽은 재사용 가능하게 둔다.

**반목표(이렇게 되면 실패)**

- 위치 API가 잠깐 빠졌다고(이번 점검: 6호선 11분 INFO-200, 9호선 등 반쪽 응답) "열차 없음"·"운행 종료"로 보이는 것. 위치가 없으면 지금처럼 도착 API·시간표로 보인다.
- 같은 열차가 두 번 보이는 것(도착 API 열차와 위치 계산 열차, 위치 계산 열차와 시간표 열차).
- 위치 계산이 시간표보다 근거 없이 우선해 오히려 틀리는 것: 구간 시간이 빠진 구간, 갈래가 모호한 열차는 계산하지 않는다.
- 새로 고칠 때마다 시각이 크게 뒤로 튀는 것(위치 API는 "출발 → 같은 역 진입" 순서 뒤틀림이 있다, 11-20 2호선 1.4%).

## 4. 제약

- **서버**: FastAPI, Render 무료(512MB). 위치 API는 노선마다 한 번 부르면 그 노선 열차 전부가 온다(`/realtimePosition/0/200/{호선}`, 수집기와 같은 형식, `server/ml/collector.py`). 실시간 키는 한도 없음(운영 기록). 그래도 노선별로 20초 캐시한다(도착 API와 같은 `ARRIVALS_TTL_SEC`).
- **구간 시간**: 서버는 이미 B2를 받는다(`MeasuredData.hop_seconds`, 시간대 → 요일 → 전체 순 중앙값, 도착→다음 도착이라 정차 포함, 일반·급행 따로). 하지만 **1~9호선은 서버용 결과물에 역 연결표(`stations`, `statn_of`)가 빠져 있어** 지금은 1~9호선 구간 시간을 찾지 못한다(`ml/publish.py`의 `server_b1`이 1~9호선 `stations`를 거른다). 서버용 결과물에 1~9호선 `stations`만 넣는다(칸·시각은 넣지 않는다). VM에 반영하고 다음 정기 배포(03:30) 뒤부터 1~9호선이 계산된다. 그 전에는 1~9호선은 지금처럼 동작한다.
- **위치 API 원천 문제**(`docs/measurements/seoul-api-known-issues.md`): 일부·전체 누락, 출발·진입 순서 뒤틀림, `recptnDt` 미래·지연, 공유 구간 노선 섞임(서해선·경의중앙선 능곡·대곡). 위치의 `statnTid`·`statnTnm`은 **종착역**이다(도착 API와 뜻이 다르다).
- **역 연결**: 위치 API의 `statnId`는 우리 역 id와 체계가 다르다. 호선 + 역명(`statnNm`)으로 `StationIndex.resolve`해 잇는다(수집기와 같은 방법).

## 5. 접근(고른 것: A)

| 방식 | 내용 | 장단점 | |
|---|---|---|---|
| **A 위치 + 구간 시간** | 현재 위치에서 이 역까지 B2 구간 시간을 더함 | 모든 노선에 같은 방법, 열차 번호 불필요, 지금까지 지연 반영. 앞으로의 지연·일부러 서 있는 시간은 못 봄 | **고름** |
| B 시간표 + 지연 | 열차 번호로 시간표를 찾아 지금 지연을 더함 | 정차·대피 패턴까지 반영. 번호가 안 맞는 노선이 많음(1호선 K번호 대 4자리, 2호선 매일 다름) | 안 함 |
| C 섞기 | 번호가 맞으면 B, 아니면 A | 가장 정확할 수 있으나 가장 큼 | 안 함(나중에 A 위에 얹을 수 있음) |

사용자 질문 "현재 위치로 계산할 수 있지 않나, 번호가 맞아야 하나?"에 대한 답으로 A로 정했다.

## 6. 계산(정한 것)

열차 하나의 이 역 도착 예정 시각:

1. **이 역으로 오는 열차인지**: 같은 호선·같은 방향이고, 현재 역에서 방향을 따라 이 역에 닿으며, 행선지(`statnTnm`)가 이 역을 지나서 있거나 이 역이다. 이 역이 종착이면 탈 수 없으므로 뺀다(도착 화면 규칙과 같다). 갈래(1호선 경부·경인·광명, 2호선 성수·신정지선, 경의중앙선 등)에서 경로가 하나로 정해지지 않으면 계산하지 않는다.
2. **구간 합**: 현재 역 → 이 역까지 이웃 구간의 `hop_seconds(급행 여부, at=지금)`을 더한다. 하나라도 없으면 계산하지 않는다(시간표로 넘김).
3. **현재 상태 보정**: 위치의 상태(`trainSttus` 0 진입·1 도착·2 출발·3 전역출발)와 `recptnDt`로 기준 시각을 정하고, 받은 뒤 지난 시간을 뺀다. `recptnDt`가 미래면 지금으로 본다. 10분 넘게 오래된 행은 쓰지 않는다. 구체 보정값은 6.1.
4. 결과가 지금보다 이르면 지금(곧 도착)으로 둔다.

### 6.1 구현에 맡기는 것

- 상태별 보정: 출발(2)이면 이미 정차를 끝낸 것이므로 첫 구간에서 정차분을 덜어야 한다. B2의 `dwell`·`lead` 표를 서버용 결과물에 더할지(작다), 호선별 정차 중앙값으로 근사할지 정한다.
- 급행: B2 급행 구간은 "다음에 도착이 찍힌 역까지"라 정차하지 않는 역을 건너뛴다. 이웃 한 칸이 없으면 몇 칸 앞까지 건너뛴 구간을 찾는 식으로 정한다.
- 경로 찾기: `station_directions`(방향별 다음 역)와 실측 운행 패턴(`TripsData`) 중 무엇으로 갈래를 풀지.
- 순서 뒤틀림(출발 뒤 같은 역 진입)으로 새로 고칠 때 시각이 뒤로 튀는 것을 어떻게 누를지. 예: 같은 열차의 직전 계산보다 크게(예 60초 넘게) 늦어지면 직전 값과 새 값 중 무엇을 낼지 규칙을 정하고 기록한다.

## 7. 합치기·표시

- **[지금]**: 도착 API 열차의 `btrainNo`와 위치 API의 `trainNo`가 같으면 같은 열차다(둘 다 서울시 실시간 원천). `barvlDt`가 0이면 그 열차를 위치 계산 값으로 바꾸고 근거를 "위치 계산"으로 한다. 위치에서 못 찾으면 지금의 문구 어림 그대로, 근거 "실시간".
- **[시각 선택] 60분 안**: 도착 API에 있고 `barvlDt`가 0보다 큰 열차는 그 값을 쓰고 근거 "실시간"이다(설계자 판단). 그 밖에는 그 역·방향으로 오는 위치 계산 열차 중 고른 시각 이후를 시각순으로 최대 4대(지금 시간표 개수와 같다). 모자라면 시간표 열차를 더하되, 마지막 위치 계산 열차보다 1분 넘게 뒤인 것만 더해 같은 열차가 두 번 보이지 않게 한다.
- **근거 표시**(열차 줄마다, 작은 표식): 실시간 / 위치 계산 / 시간표 / 실측. 지금은 방향 단위(`DirectionTrains.basis`)로만 있다. 열차 단위로 옮긴다.

```
상행 · 종각 방면
  동두천행  4분  12:31 도착  [위치 계산]
  그다음 9분(12:36) [위치 계산]
```

## 8. 서버 응답(제안, 구현에서 바꿔도 됨)

- `Train`에 `basis`(`realtime` | `position` | `timetable` | `measured`)를 더한다. 예전 앱은 무시한다.
- [시각 선택] 60분 안은 `GET /v1/stations/{id}/arrivals?at=ISO시각`으로 받는다(없으면 지금). 앱은 고른 시각이 60분 안이면 이것을, 아니면 지금처럼 `/timetable`을 부른다.
- 위치 API 실패·빈 응답은 오류로 올리지 않는다. 그 노선은 위치 계산 없이 지금처럼 답한다.

## 9. 성공 기준과 노선별 켜기

켜기 전에 VM 수집 데이터(위치 API 이벤트, 원본 응답 14일)로 노선마다 되돌려 본다(backtest). 실제 도착 시각은 위치 이벤트의 도착(1) 시각이다.

- **[지금] 켜기(코레일 원천 노선)**: VM은 도착 API 응답을 저장하지 않으므로, 지금의 문구 어림은 위치 기록으로 다시 만든다(그 시점 열차가 몇 역 앞인지 × 120초, 설계자 판단). 같은 관측에서 "문구 어림"과 "위치 계산"을 실제 도착에 견준다. **위치 계산의 MAE가 더 작고 ±60초 비율이 같거나 높을 때만** 그 노선을 켠다.
- **[시각 선택] 켜기(모든 노선, 사용자 결정 2026-11-22 "견줘봐")**: 5~60분 앞을 내다본 위치 계산을 같은 열차의 시간표(1~9호선 공식, 그 밖은 실측 B1)와 실제 도착에 견준다. **위치 계산이 시간표보다 MAE가 작은 노선에서만** [시각 선택]에 쓴다. 지평(5·15·30·60분)별 결과를 문서에 적는다. 내다보는 거리가 길어질수록 나빠지면, 노선별로 쓸 수 있는 최대 분을 정해도 된다.
- **켜고 끄기**: 노선별 목록을 서버 설정에 둔다(`[지금]`용, `[시각 선택]`용 따로). 평가 결과로 채우고, 결과 표를 `docs/ml/`에 남긴다.
- 위치 API가 비거나 일부만 와도 화면이 지금보다 나빠지지 않는다(테스트로 확인).
- 같은 열차가 두 번 보이지 않는다(테스트로 확인).

## 10. 반영 순서

1. VM: `server_b1`에 1~9호선 `stations` 넣기 → VM `git pull`(VM을 건드리기 전에 사용자에게 확인) → 다음 03:30 배포. 그 전 서버 테스트는 픽스처로 한다.
1.5. 평가: VM 데이터로 9장의 되돌려 보기를 돌려 노선별 켜기 목록을 정한다(VM에서 읽기만).
2. 서버: 위치 받기(캐시) + 계산 + 합치기 + `basis` + `at`. Render 배포.
3. 앱: 열차 단위 근거 표시, [시각 선택] 60분 안이면 `arrivals?at=`.

앱이 나중에 나가도 서버 쪽 1·2는 [지금]의 코레일 노선을 바로 좋게 한다.
