# 실시간이 없을 때의 열차 도착 예측 모델 — 계획 초안

- 작성: 2026-11-13. 구현은 별도 세션에서 한다. 이 문서는 그 세션의 출발점이다(설계 확정 전 초안).
- 관련 문서: 재설계 스펙 `docs/superpowers/specs/2026-11-12-simple-subway-redesign.md`, 위치 API 정리 `docs/superpowers/specs/2026-11-05-train-position-fusion-design.md` 4.1절(폐기된 기능이지만 API 사실은 유효), 실기기 점검 `docs/measurements/device-checklist.md`.

## 1. 풀려는 문제

지금 앱은 "다음 열차"를 실시간 도착 API → 서울시 시간표 순으로 구한다. 다음 경우에는 열차 정보가 없거나 부정확하다.

| 경우 | 지금 | 모델이 줄 수 있는 것 |
|---|---|---|
| 시간표가 없는 노선(1호선, 경의중앙선, 수인분당선, 공항철도, 신분당선, 경춘선, 우이신설선, 신림선, 경강선, 서해선, GTX-A — 2026-11-12 확인) | "+1시간", 시각 선택, 루틴 미리보기, 환승 열차가 비어 있음 | 관측으로 만든 "실측 시간표" |
| 실시간이 없는 역(진접, 별내별가람 등)·실시간 API 장애·호출 한도 초과 | 시간표 대체(2~9호선만) | 마지막으로 본 열차 위치 + 학습한 구간 시간으로 추정 |
| 시간표대로 다니지 않는 열차(지연) | 시간표 시각을 그대로 보임 | 요일·시간대·구간별 지연을 반영한 보정 |

목표: **역 S, 호선 L, 방향 D, 기준 시각 t가 주어지면 t 이후 그 역을 떠나는 열차 2~4대의 예상 시각**을 준다. 지금 응답 형식(`source`)에 `"predicted"`를 더해 앱이 "예측"으로 표시한다.

## 2. 데이터 수집

### 2.1 출처: 서울시 실시간 열차 위치정보(`realtimePosition`)

- 요청: `http://swopenapi.seoul.go.kr/api/subway/{키}/json/realtimePosition/0/200/{호선명}`. 한 번에 그 호선의 모든 열차.
- 쓸 필드: `trainNo`, `statnId`/`statnNm`(지금 역), `trainSttus`(0 진입, 1 도착, 2 출발, 3 전역출발), `recptnDt`(이벤트 시각), `updnLine`, `statnTid`(종착역), `directAt`(급행), `lstcarAt`(막차).
- 알려진 문제: `recptnDt`가 오래되거나(실측 18분) 미래로(최대 +160초) 올 수 있다. 일부 역 누락 보고가 있다.
- 실시간 도착 API(`realtimeStationArrival`)는 역 단위라 수집 비용이 커서 보조로만 쓴다.

### 2.2 호출 한도가 가장 큰 제약

- 키 하나에 하루 1,000회. 쓸 수 있는 키는 위치 전용 키와 예비 키 2개 해서 3,000회 정도다. 서버가 쓰는 실시간 키는 건드리지 않는다.
- 한 호선을 60초마다 첫차부터 막차까지(약 19.5시간) 부르면 하루 약 1,170회다. 키 하나에 한 호선 정도가 된다.
- 기본안: **사용자가 실제로 타는 호선 2~3개**를 60초 간격으로 모은다. 더 넓히려면 출퇴근 시간대(06–10시, 17–21시)만 모은다.
- `recptnDt`가 이벤트 시각이라, 60초 간격으로 불러도 도착·출발 시각 자체는 그보다 정확하다(같은 이벤트는 중복 제거).

### 2.3 수집기를 돌릴 곳

- Render 무료 서버는 잠들므로 맞지 않는다. GitHub Actions cron은 최소 5분 간격이고 늦게 뜰 때가 있다.
- 후보:
  - (a) 개발 PC에서 항상 도는 스크립트(작업 스케줄러)
  - (b) 무료 상시 VM(예: Oracle Cloud Always Free)
  - (c) Render 유료 백그라운드 워커
- 기본안은 (a)로 시작해 2주 이상 돌린다. 꺼짐에 대비해 매일 백업한다.

### 2.4 저장 형식

- `raw_snapshots`(호선, 받은 시각, 응답 JSON 그대로): 나중에 파싱 규칙을 바꿔도 다시 만들 수 있게 한다.
- `events`(날짜, 요일 구분[평일·토·휴일, `holidays` KR], 호선, 방향, `trainNo`, 역 id, 상태[진입·도착·출발], 이벤트 시각, 종착역, 급행, 막차): `(날짜, 호선, trainNo, 역, 상태)`로 중복을 지우고 가장 이른 `recptnDt`를 쓴다.
- 우리 역 id로 잇기: `StationIndex.resolve(statnNm, 호선)`. 실시간 역 id(`statnId`)와 우리 id 대응표를 함께 만든다.
- SQLite로 시작하고, 커지면 날짜별 Parquet로 옮긴다. 키는 저장하지 않는다(URL 마스킹 규칙 재사용).

## 3. 먼저 확인할 것(수집 첫 주 분석)

1. 같은 시간표 칸의 열차가 날마다 같은 `trainNo`를 쓰는가(같은 요일 구분 기준)? 그렇다면 "열차 번호별 실측 시간표"가 가장 단순하고 강한 모델이다.
2. `trainSttus` 도착→출발 간격(정차 시간)과 역 간 이동 시간 분포는 어떤가?
3. `recptnDt` 오류(과거·미래로 튄 값)는 얼마나 자주 생기고, 어떻게 걸러 낼까?
4. 2~9호선에서 실측과 공식 시간표(`LEFTTIME`)의 차이(지연)는 얼마나 나는가? 이 차이가 작으면 시간표가 있는 노선은 모델 효과가 작다.

## 4. 모델(단순한 것부터)

평가 기준은 모두 같다. 날짜로 나눈 시험 세트에서 예측 출발 시각과 실측 출발 시각의 차이를 본다. MAE(초), 90백분위 오차, ±60초·±120초 안에 든 비율.

| 단계 | 모델 | 쓰는 곳 |
|---|---|---|
| B0 | 공식 시간표 그대로(2~9호선) | 기준선 |
| B1 | **실측 시간표**: (요일 구분, 호선, 방향, 역, `trainNo`)별 출발 시각의 중앙값. `trainNo`가 날마다 다르면 시간대별 배차 간격 중앙값으로 열차 시각을 만든다 | 시간표가 없는 노선, 미래 시각 |
| B2 | **구간 시간 추정**: 마지막으로 본 열차 위치 + (요일, 시간대, 구간)별 이동 시간·정차 시간 중앙값의 합 | 실시간이 끊긴 직후, 실시간 없는 역 |
| M1 | **보정 모델**: LightGBM 같은 표 데이터 회귀로 B1·B2의 오차를 예측해 더한다. 특징은 요일 구분, 시간대(분), 역 순서, 남은 정거장 수, 마지막 관측 뒤 지난 시간, 그날 그 호선의 최근 지연, 급행·막차 여부 | B1·B2보다 확실히 좋을 때만 |

- 딥러닝은 쓰지 않는다. 데이터 양(호선 몇 개 × 몇 주)과 설명 가능성을 생각하면 중앙값 표 + 트리 모델이 맞다.
- 학습은 오프라인 스크립트로 한다. 결과물(중앙값 표, LightGBM 모델 파일)은 서버 `data/`에 넣고 요청할 때는 읽기만 한다.

## 5. 서버·앱 통합

- 서버 `TimetableService` 옆에 `PredictionService`를 둔다. 순서는 실시간 → 공식 시간표 → 예측 → 없음이다. 시간표가 없는 노선은 예측이 대신한다.
- 응답 `source`에 `"predicted"`를 더한다. 앱은 "예측"이라고 표시한다(시간표 기준과 구분).
- 신뢰도가 낮으면(학습 데이터 부족, 해당 요일·시간대 관측 수 N 미만) 예측하지 않는다.
- 모델 갱신: 주 1회 다시 학습한다. 모델 파일에 버전과 학습 기간을 기록한다.

## 6. 단계와 일정(제출 11/25와 분리)

1. 수집기(위치 API → raw·events, 한도 보호, 중복 제거, 백업): 1~2일. **바로 시작해야 데이터가 쌓인다.**
2. 첫 주 분석(3절 질문): 데이터 7일 뒤
3. B1·B2와 평가 스크립트: 데이터 2주 뒤
4. 서버 통합(`predicted`): 평가에서 B0보다 나을 때
5. M1: 데이터 4주 이상 쌓인 뒤 선택

## 7. 위험

- 호출 한도: 수집기가 서버 키를 쓰면 앱이 멈춘다. 키를 반드시 나누고, `ERROR-337`이면 멈춘다.
- 위치 API 품질: 누락 역, `recptnDt` 오류. 이상값을 걸러 내는 규칙과 관측 수 하한이 필요하다.
- 비서울 5개 노선은 위치 API에도 없을 가능성이 크다. 수집 첫날 확인한다.
- 개인 정보: 열차 공개 데이터만 쓴다. 사용자 위치·기록은 모으지 않는다.

## 8. 별도 세션이 사용자에게 물을 것

1. 모을 호선(기본: 사용자가 실제로 타는 호선 2~3개)
2. 수집기를 돌릴 곳(기본: 개발 PC)
3. 수집 시간대(종일 vs 출퇴근 시간대)
4. 예비 키 2개를 수집 전용으로 써도 되는지
