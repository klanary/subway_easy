# 안드로이드 앱 화면 다듬기: 화면별 상태를 하나씩 — 설계

- 날짜: 2026-11-20
- 범위: `android/app` UI 계층(`ui/**`, `ui/theme`, `ui/common`). 서버·웹 화면은 범위 밖.

## 1. 의도와 이유

앱 전체가 "쓰기 좋지 않다". 특정 화면 하나의 문제가 아니라 처음부터 끝까지 고르게 거칠다.
그래서 사용 흐름을 따라 **화면마다 나올 수 있는 상태를 빠짐없이 짚고**, 상태별로 무엇이 보이고 어떻게 움직여야 하는지 정해 고친다.

지금 코드에서 확인한 사실:

- 공통 상태 틀 `UiState`(Loading·Content(stale)·Empty·Error·Offline)와 `StateContainer`가 있지만, `StateContainer`를 쓰는 화면은 경로 결과(`RoutesScreen`) 하나뿐이다.
- 역 시트·검색은 `UiState`를 각자 `when`으로 그린다(진행 막대, 문구 한 줄). 노선도 홈·경로 상세·루틴·세션·설정은 `UiState` 밖에서 화면마다 따로 상태를 들고 있다(예: `LineMapUiState.map == null`일 때 아무 표시 없음).
- 결과: 같은 "불러오는 중/오류"도 화면마다 모양이 다르고, 어떤 상태는 아무것도 안 보인다. 실제 에뮬레이터에서 앱을 열면 노선도가 그려지기 전 몇 초 동안 검색창과 하단 탭만 있는 빈 화면이 나온다.
- 오래된 정보(stale)는 내용 전체를 50% 흐리게 하고 칩을 붙인다. 오류는 가운데 문구 + "다시 시도" 버튼뿐이다.
- `@Preview`가 하나도 없다. Robolectric은 이미 테스트 의존성에 있다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 모든 화면에서, 모든 상태가 무언가를 보여 주고(빈 화면 없음) 사용자가 다음에 할 일을 알 수 있다.
- 같은 종류의 상태는 앱 어디서나 같은 모양·같은 말투로 보인다.
- 화면별로 쓰기 불편한 동작(터치 영역, 흐름 끊김, 문구 등)을 그 화면을 다룰 때 함께 고친다.
- 각 상태를 기기 없이 다시 볼 수 있는 스크린샷 테스트가 남는다.

**비목표**
- 서버 API, 경로 탐색 로직, 데이터 계층 변경(화면이 상태를 받기 위해 필요한 최소한의 ViewModel 정리는 포함).
- 웹 화면.
- 새 기능 추가.

**반목표(이러면 실패)**
- 지금 잘 되는 동작(열차 고르기, 출발 알림, 루틴 복원)을 깨뜨리는 것. 기존 단위 테스트는 계속 통과해야 한다.
- 화면 전체를 새로 짜서 원래 흐름이 바뀌는 것. 다듬기이지 재설계가 아니다.
- 한 번에 모든 화면을 바꾸고 마지막에 몰아서 확인하는 것.

## 3. 제약

- 경로에 한글이 있어 `android.overridePathCheck=true`를 쓰고 `-Dfile.encoding=UTF-8`은 넣지 않는다(기존 설정 유지).
- 확인용 기기: 에뮬레이터 `pixel8`(API 36, x86_64). Vanguard 경고가 뜨지만 동작한다.
- 문구는 `ui/common/Copy.kt`에 모아 둔다(기존 관례).

## 4. 접근 방식

| 방식 | 내용 | 장단점 |
|---|---|---|
| **A. 흐름 순서대로 한 화면씩 (선택)** | 공통 상태 모양을 먼저 다듬고, 홈부터 설정까지 한 화면씩 상태 목록 → 현재 모습 → 고칠 점 합의 → 반영 → 확인 | 사용자가 화면마다 직접 보고 결정한다. 가장 느리다. |
| B. 기반 먼저, 화면 일괄 적용 | 색·글자·간격과 공통 상태 컴포넌트를 정하고 전 화면에 한 번에 적용 | 빠르지만 화면별 사용 불편을 놓친다. |
| C. 목업으로 새로 설계 | 브라우저 목업으로 전체 재설계 후 구현 | 잘 되는 동작까지 다시 만들게 되어 위험. |

사용자가 A를 골랐다. 확인 수단은 **에뮬레이터(흐름·손맛) + 상태별 스크린샷 테스트(만들기 어려운 상태)**로 정했다.

## 5. 진행 방식

### 5.1 순서

0. **준비:** 상태별 스크린샷 테스트 틀(Roborazzi + 기존 Robolectric). 테스트에서 화면 컴포저블에 가짜 상태를 바로 넣을 수 있도록, 화면을 "상태를 받는 컴포저블"과 "ViewModel을 연결하는 겉껍데기"로 나눈다(이미 나뉜 화면은 그대로).
1. **공통 상태 모양:** 불러오는 중·빈 화면·오류·오프라인·오래된 정보를 전체 화면용과 시트/목록 안 인라인용 두 크기로 정리하고, `Copy.kt` 말투를 맞춘다.
2. 노선도 홈 (`ui/linemap/LineMapScreen`, 홈 하단 탭: 루틴·자주 가는 경로)
3. 역 시트 (`ui/linemap/StationSheet`)
4. 검색 (`ui/search`)
5. 경로 편집·결과 (`ui/routeedit`, `ui/routes`)
6. 경로 상세·열차 고르기 (`ui/routedetail`)
7. 루틴 목록·편집 (`ui/routine`)
8. 세션(진행 중 알림)과 시작 흐름 (`ui/session`)
9. 설정·권한 (`ui/settings`)

### 5.2 화면마다 하는 일 (한 화면 = 한 바퀴)

1. **상태 목록:** 그 화면에 나올 수 있는 상태를 코드에서 모두 뽑는다. 기본 다섯 가지(`UiState`)에 화면 고유 상태를 더한다. 예: 노선도는 "역 위치표 읽는 중", "위치 권한 없음", "가까운 역 없음", 출발·도착 고르는 중. 역 시트는 미지원 노선, 시간표 없는 노선, 막차 이후, +1h/+2h 시각.
2. **현재 모습:** 상태별 스크린샷과 에뮬레이터 화면을 사용자에게 보여 준다.
3. **합의:** 상태별로 고칠 점을 제안하고 사용자가 고른다. 화면의 사용 불편(버튼 위치, 문구, 터치 영역 등)도 이때 함께 다룬다.
4. **반영:** 고친다. 상태별 스크린샷 테스트를 추가·갱신한다.
5. **확인:** 기존 단위 테스트를 통과하고, 에뮬레이터에서 흐름을 직접 확인한 뒤 사용자에게 전후를 보여 준다.
6. **커밋:** 화면 하나당 커밋 하나 이상, `develop`에서 브랜치를 따서 진행한다.

### 5.3 산출물

- 화면별 상태 표(상태 → 보이는 것 → 할 수 있는 일)를 이 문서 부록에 화면을 마칠 때마다 덧붙인다.
- 스크린샷 기준 이미지(Roborazzi)를 저장소에 둔다.

## 6. 정해진 것 / 빌더에게 맡기는 것

**정해진 것(사용자 결정)**
- 대상은 안드로이드 앱, 방식 A, 흐름 순서, 에뮬레이터 + 스크린샷으로 확인.
- 화면마다 사용자가 보고 결정한다. 각 화면의 구체적 모양은 그 바퀴에서 정한다.

**세부 결정 사항(변경 가능)**
- 스크린샷 도구는 Roborazzi. 이유: 이미 Robolectric이 있어 추가 부담이 가장 적다.
- 공통 상태 모양을 맨 먼저 한다. 이유: 뒤 화면들이 같은 조각을 가져다 써야 일관된다.
- 작업 브랜치는 바퀴(단계)마다 `develop`에서 따고, 그 바퀴를 사용자가 확인하면 `develop`에 합친다. 이유: 마지막에 몰아서 확인하지 않기 위해서다.
- 1단계(공통 상태 모양)도 화면처럼 한 바퀴로 다룬다. 전후 스크린샷을 보여 주고 사용자가 정한다. 오래된 정보를 흐림과 칩으로 보여 주는 지금 방식을 바꿀지도 이때 정한다.
- 문구 말투는 지금 `Copy.kt`가 쓰는 해요체("~했어요", "~해 주세요")를 기준으로 한다.
- 스크린샷 기준 이미지는 라이트·다크 두 가지로 남긴다(기본 글꼴 크기, Pixel 8 폭). 큰 글꼴은 에뮬레이터 확인 때 한 번씩만 본다.
- 노선도 SVG가 Robolectric에서 제대로 안 그려지면, 스크린샷에서는 노선도 영역을 자리표시로 두고 그 위의 상태 표시층만 검증한다. 노선도 실제 모습은 에뮬레이터로 확인한다.
- 계획은 0·1단계를 자세히 쓰고, 2~9단계는 5.2의 바퀴를 되풀이하는 틀로 둔다. 각 바퀴의 3번(합의)에서는 반드시 멈추고 사용자를 기다린다. 화면별 구체적 수정은 그 바퀴에서 정해 계획에 덧붙인다.

**빌더에게 맡기는 것**
- 화면 컴포저블을 상태/겉껍데기로 나누는 세부 방법.
- 스크린샷 테스트의 가짜 데이터 구성.
