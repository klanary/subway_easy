# 42. 역 기준 데이터 빌드

> Claude Code가 쓴 초안이다. 본인이 직접 고쳐 쓴다(스펙 12절).

- 무엇을 만들었나: 서울시 역사마스터 원본(784행)을 읽어 서버가 쓰는 `stations.sqlite`(역, 역-호선 연결, 별칭)를 만드는 `scripts/build_stations.py`, 원본을 OpenAPI로 내려받는 `scripts/fetch_station_master.py`.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 같은 이름의 역은 호선이 달라도 한 역으로 묶는다. 서울시 실시간 API가 역 이름으로 조회하면 모든 호선을 함께 주기 때문이다. 좌표는 호선 좌표의 평균이다.
  - 이름이 같아도 1km 넘게 떨어져 있으면 빌드를 실패시킨다(5호선 양평과 경의중앙선 양평). 조용히 평균을 내면 두 역 사이의 엉뚱한 곳이 "양평역"이 된다. 실패 메시지를 보고 "별도 역 표"에 더해 나눈다.
  - 괄호 이름은 별칭으로 뗀다("총신대입구(이수)" → 별칭 "이수"). 다만 별칭이 다른 역의 이름과 같으면 만들지 않는다. 7호선 이수역이 따로 있기 때문이다.
  - 서버가 시작할 때마다 원본을 읽지 않고 미리 만든 SQLite 파일을 커밋한다. 배포 서버에는 원본도 키도 필요 없고, 같은 입력이면 같은 파일이 나와 바뀐 내용을 diff로 볼 수 있다.
  - 열 이름은 내려받은 파일(한글)과 OpenAPI(`BLDN_ID` 등) 둘 다 읽는다. 실제 응답을 받아 보니 OpenAPI 쪽 이름이 스펙을 쓸 때 가정한 것과 달랐다.
- 막혔던 점과 해결:
  - 처음에는 "원본 파일이 없어 시작할 수 없다"고 미뤘다. 공식 샘플 키로 5행을 받아 열 이름과 값 형식을 먼저 확인하고, 합성 데이터로 규칙을 테스트한 뒤 실제 데이터는 키를 받으면 돌리기로 했다.
- 예상 면접 질문과 내 답:
  - Q. 왜 역 id를 숫자 코드가 아니라 이름으로 했나? A. 실시간 API는 이름으로 조회하고, 카카오 경로 응답도 정차역 이름만 준다. 두 출처를 잇는 공통 열쇠가 정규화한 이름이다.
  - Q. 빌드가 같은 결과를 낸다는 것은 어떻게 확인했나? A. 두 번 만든 SQLite의 덤프를 비교하는 테스트가 있다. 결과를 정렬해서 쓰기 때문에 입력 순서가 달라도 같다.
