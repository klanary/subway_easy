# 04. 오류 형식, 공통 모델, 앱 조립

- 무엇을 만들었나: 스펙 6.3의 오류 응답 형식(`{"error": {"code", "reason", "message"}}`)과 오류 클래스 계층, 한국 시간 도구(`KST`, `kst_from_epoch`), camelCase 응답 모델의 부모(`ApiModel`), 의존 객체 묶음(`AppServices`)과 `create_app`의 조립 방식, 테스트 도구(`FakeClock`, `load_fixture`, `fixture_response`).
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 오류를 예외 클래스로 만들고 FastAPI 예외 처리기 하나에서 응답으로 바꾼다. 서비스 코드는 `raise NoRoute("NO_START_STOP")`만 하면 되고, HTTP 상태·코드·문구는 한곳에서 관리된다. 엔드포인트마다 `JSONResponse`를 직접 만들면 형식이 어긋나기 쉽다.
  - 파라미터 검증 실패(FastAPI 기본은 422)도 400 `INVALID_REQUEST`로 바꾼다. 앱이 처리할 오류 코드가 스펙 표 하나로 정해진다.
  - 외부 API 실패 3종(502·503·504)은 공통 부모 `UpstreamFailure`를 둔다. 캐시가 "외부 실패면 만료 데이터로 대신 응답"을 한 번의 `except`로 처리할 수 있다.
  - 시계를 `clock()` 함수로 주입한다. 테스트가 `FakeClock`으로 시간을 움직여 캐시 만료·자정 초기화 같은 시간 의존 동작을 기다리지 않고 확인할 수 있다.
  - 한국 시간은 `timezone(timedelta(hours=9))` 고정 오프셋이다. 서머타임이 없어 정확하고, Windows·slim 이미지에 tzdata가 없어도 된다.
- 막혔던 점과 해결:
  - P1의 `create_app`은 설정을 `app.state.settings`에 두었는데, 이후 작업이 캐시·클라이언트 등을 계속 더하므로 `app.state.services` 하나(`AppServices`)로 모았다.
- 예상 면접 질문과 내 답:
  - Q. 오류 응답에 사용자 문구까지 서버가 주는 이유는? A. 앱은 코드에 따라 분기만 하고 문구는 그대로 보여주면 된다. 문구를 고칠 때 앱을 다시 배포하지 않아도 된다.
  - Q. 왜 422 대신 400인가요? A. 스펙의 오류 표를 앱과 서버가 함께 쓰는 계약으로 두었다. 검증 실패도 "요청 형식 오류"라는 같은 의미라 하나의 코드로 묶었다.
