# 77. 밤마다 변경 판단과 B1 다시 만들기

- 무엇을 만들었나: `server/ml/nightly.py`(`python -m ml.nightly`). 상태를 읽고, 아직 안 뽑은 날을 날짜순으로 파생 DB에 뽑아 변경을 판단하고, 호선마다 B1을 만들어 한 결과물(`ml_data/artifacts/measured_timetable.json`)로 합치고, 상태 파일과 변경 기록(`changes.md`)을 쓴다. 기본은 관찰 모드(확정된 변경을 기록만 하고 B1에는 적용하지 않음)이고 `--enforce`를 주면 적용한다.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 같은 밤에 다시 돌려도 결과가 같게 했다. 이미 뽑은 (날짜, 호선)과 이미 판단한 날은 건너뛴다. 타이머가 두 번 돌거나 손으로 다시 돌려도 기록이 중복되지 않는다.
  - VM이 며칠 꺼졌다 켜지면 빠진 날을 날짜순으로 따라잡는다(14일까지). 순서가 중요해서(의심 → 확정), 어느 날의 판단이 실패하면 그 뒤 날짜는 건너뛰지 않고 판단을 멈춘다.
  - 한 호선의 B1이 실패해도 나머지는 만든다. 실패한 호선의 칸은 이전 결과물에서 그대로 옮기고 종료 코드 1로 알린다. 열아홉 호선 가운데 하나 때문에 전체 시간표가 비는 것보다 낫다.
  - 결과물과 상태 파일은 임시 파일에 쓴 뒤 바꾸고, 바꾸기 전 것을 `.prev`로 남긴다.
  - 알림은 확정만 보낸다. 의심은 하루짜리 지연이 대부분일 것이라 기록만 한다. 알림이 실패해도 밤 작업은 실패하지 않는다.
- 막혔던 점과 해결:
  - VM의 실제 하루치(2026-11-16, 이벤트 43만 건, DB 139MB)로 개발 PC에서 재 보니 8.9초, 메모리 최대 142MB였다(목표 5분·400MB 안). 출발 시각은 하루 20만 건, 파생 DB는 하루 약 27MB였다. 처음 정한 보관 120일이면 3GB가 넘어, 창이 가장 긴 토·휴일 8주를 덮는 70일로 줄였다.
  - 출발 20만 건 가운데 절반은 "도착 + 정차 시간"으로 어림한 값이었다. 출발이 안 찍히는 노선이 그만큼 많다.
  - 실제 수집 횟수를 보니 05시대는 105회(첫차 전 "데이터 없음"), 나머지는 120회였다. 기준 96회(80%)가 정상인 날을 떨어뜨리지 않는다.
  - 테스트용 DB에 raw 응답이 없으면 수집 횟수가 "모름"이라 아무것도 의심하지 않는다. 테스트가 시간대마다 정상 응답 120건을 넣게 했다.
- 예상 면접 질문과 내 답:
  - Q. 매일 도는 작업을 다시 돌려도 안전하게 만들려면?
  - A. 각 단계가 "이미 했으면 건너뛴다"를 스스로 판단하게 하고, 마지막 쓰기는 임시 파일에 쓴 뒤 이름을 바꾼다. 그리고 "두 번 돌린 뒤 상태 파일과 결과물이 같다"를 테스트로 고정한다.
