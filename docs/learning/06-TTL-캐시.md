# 06. 동시 요청 합치기와 만료 데이터 보관을 갖춘 TTL 캐시

- 무엇을 만들었나: 키별 유효 시간 캐시(`TtlCache`)와 서버 지표(`Metrics`). 유효 시간 안이면 저장값(hit), 같은 키의 외부 호출이 진행 중이면 그 결과를 함께 기다리고(hit), 외부 호출이 실패하면 보관 기간(24시간) 안의 만료 값을 `stale`로 돌려준다.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - Redis 대신 직접 만든 메모리 캐시다. 서버가 한 대라 프로세스 메모리로 충분하고, 동작을 직접 설명할 수 있다(스펙 5.3).
  - 동시 요청 합치기: 출근 시간에 같은 역을 여러 명이 동시에 조회해도 서울시 API는 한 번만 부른다. 진행 중인 호출을 `asyncio.Task`로 표에 넣고, 뒤따른 요청은 그 작업을 기다린다. 일일 1,000회 한도를 지키는 핵심이다.
  - `asyncio.shield`로 기다린다. 먼저 온 요청의 사용자가 앱을 닫아 그 요청이 취소돼도, 공유 작업은 취소되지 않아 함께 기다리던 요청이 정상 응답을 받는다.
  - 값 저장은 작업의 완료 콜백에서 한다. 작업을 만든 요청이 취소돼도 결과가 캐시에 남는다.
  - 외부 실패(502·503·504)일 때만 만료 값으로 대신한다. `NoRoute` 같은 "정상적인 없음"은 그대로 알려야 하므로 가리지 않는다. 실패는 저장하지 않아 다음 요청이 다시 시도한다.
- 막혔던 점과 해결:
  - 함께 기다리는 요청이 깨어났을 때 값이 이미 저장돼 있어야 `fetched_at`을 맞게 돌려줄 수 있다. 완료 콜백은 작업을 만들 때 가장 먼저 등록하므로, `shield`가 등록한 콜백보다 먼저 실행된다는 순서를 이용했다.
- 예상 면접 질문과 내 답:
  - Q. 캐시 스탬피드(만료 순간 요청이 몰려 원본을 여러 번 호출)를 어떻게 막았나요? A. 키별로 진행 중인 호출을 하나만 두고 나머지는 그 결과를 기다리게 했다(single-flight). 테스트로 동시 요청 10개가 호출 1번을 공유하는 것을 확인했다.
  - Q. 만료된 데이터를 보여줘도 되나요? A. 실시간 도착처럼 신선도가 중요한 값은 응답에 `stale: true`를 붙여 앱이 흐리게 "갱신 지연"으로 표시한다. 아무것도 안 보여주는 것보다 낫다고 판단했다.
