# 41. 위치로 탑승 자동 감지(세션 대기 중, 경로 상세)

> Claude Code가 쓴 초안이다. 본인이 직접 고쳐 쓴다(스펙 12절).

- 무엇을 만들었나: 위치를 10초마다 받는 흐름(`LocationProvider.updates`), 탈 역·다음 정거장의 좌표를 역 검색으로 얻는 `detectionTarget`, 위치 흐름에서 탑승을 기다리는 `awaitBoarding`과 서비스용 `detectBoarding`을 만들어 두 곳에 연결했다. 세션 대기 중에는 세션 서비스가 감지해 누르지 않아도 탑승 단계로 넘어가고, 경로 상세만 보던 중에는 화면이 "OO행에 타셨나요? [하차 알림 시작] [아니에요]"를 묻는다(위치 결합 스펙 7.1).
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 위치는 기기 안에서만 쓴다. 역 좌표는 서버의 역 검색으로 얻고 폰 위치는 보내지 않는다(3.2). 경로 응답에 좌표를 더하는 방법도 있었지만, 이미 있는 API로 충분하고 서버를 바꾸지 않는다.
  - 위치 흐름은 `callbackFlow`로 감싸 모으는 동안만 위치를 받는다. 화면을 떠나거나 서비스가 일을 바꾸면 흐름이 닫히며 `removeLocationUpdates`가 불려 배터리를 아낀다.
  - 감지할 수 없을 때(좌표를 못 찾음, 권한을 거둠)는 바로 끝내지 않고 기다린다. 바로 끝내면 서비스가 같은 일을 다시 골라 검색을 계속 부르는 반복이 생긴다.
  - 대기 중에는 실시간 도착 조회와 감지를 함께 돌리고, 하나가 끝나면 다른 하나를 취소한다. 사용자가 [탑승했어요]를 먼저 누르면 감지를 멈추고, 감지가 먼저면 조회를 멈춘다.
  - 경로 상세의 감지는 세션이 없을 때만 한다. 세션이 있으면 세션 서비스가 맡으므로 같은 위치를 두 번 받지 않는다. [아니에요]를 누르면 그 화면에서는 다시 묻지 않는다.
- 막혔던 점과 해결:
  - 서비스 안의 감지 코드는 안드로이드 서비스에 묶여 시험하기 어렵다. 감지 흐름 자체를 함수(`detectBoarding`)로 떼어 검색·위치·근처 열차를 바꿔 넣는 테스트를 더했다.
- 예상 면접 질문과 내 답:
  - Q. 화면이 꺼져도 감지되나? A. 세션 대기 중에는 포그라운드 서비스(유형 location)가 돌아 화면이 꺼져도 위치를 받는다. 경로 상세만 보던 경우는 화면이 보이는 동안만 한다. 위치 권한은 "앱 사용 중에만"이면 충분하다.
  - Q. 지하에서 GPS가 안 잡히면? A. 정확도 1,000m 안의 위치만 쓰므로 감지가 늦거나 안 될 수 있다. 그때는 계획한 열차를 쓰거나 직접 고르면 된다. 실기기 측정(S7)으로 감지까지 걸린 시간을 확인한다.
