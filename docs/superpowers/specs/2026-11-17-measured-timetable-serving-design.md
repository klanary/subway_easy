# 실측 시간표를 서버에 연결 — 설계 (작업 1/3)

- 작성 2026-11-17. 상위 계획: 사용자가 정한 순서 **1 실측 시간표 연결 → 2 경로 직접 계산(카카오 제거) → 3 구간별 열차 고르기**. 이 문서는 1만 다룬다.
- 관련: 예측 모델 설계 `docs/ml/2026-11-13-train-eta-model-plan.md`(§0 2026-11-17 결정: 수·일 전송), 수집기 `docs/ml/collector.md`, 변경 감지 `docs/ml/timetable-changes.md`.

## 1. 왜

- 서울시 시간표 API는 **1~9호선만** 있다(2026-11-17 확인). 경의중앙선·수인분당선·신분당선·공항철도·경춘선·경강선·서해선·우이신설선·신림선·GTX-A는 "+1시간", 시각 선택, 루틴 미리 보기, 환승 열차가 비어 있다.
- VM이 위치 API로 만드는 실측 시간표(B1)와 구간 시간(B2)이 이 빈자리를 채운다. 지금은 VM 안에만 있어 앱이 못 쓴다.
- 작업 2(경로 직접 계산)와 3(열차 고르기)은 "이 열차가 내릴 역에 몇 시에 닿는가"가 모든 노선에 필요하다. 이 문서가 그 재료를 서버에 올린다.

## 2. 목표·비목표·실패 조건

- 목표
  - VM의 결과물을 **수·일 주 2회** GitHub 릴리스로 내보내고, 서버가 받아 메모리에 둔다.
  - 시간표 API가 없는 노선의 `/timetable`과 실시간 대체(arrivals의 빈 방향)를 실측 시간표로 채운다. 응답에 출처를 `"measured"`로 표시하고, 앱은 "실측"이라고 보인다.
  - 작업 2·3이 쓸 조회 함수를 서버 안에 둔다: 역별 출발 목록, 열차 번호로 다른 역 시각 찾기, 구간 시간.
- 비목표
  - 1~9호선은 공식 시간표를 그대로 쓴다(실측으로 바꾸지 않는다).
  - 경로 계산, 열차 고르기 화면은 작업 2·3.
  - LightGBM(M1)은 하지 않는다.
- 실패 조건
  - 관측이 모자란 칸(관측 3일 미만, 변경 뒤 2일 미만, 변경 의심 중)을 내보내 틀린 시각을 보인다.
  - 결과물을 받지 못하거나 깨졌을 때 서버가 멈추거나 엉뚱한 값을 낸다.
  - GitHub 토큰이 로그·저장소에 남는다.

## 3. 사실 (2026-11-17 확인)

- B1 결과물(`measured_timetable.json`, version 2): `cells`의 키는 `요일구분|호선|방향(0 상행·내선, 1 하행·외선)|위치 API 역 id(statn_id)`. 값은 `{secs(운행일 0시부터 초, 24시 넘으면 86400 이상), train_no(없을 수 있음), n_days, dest_name, express, first_seen, last_seen, official}` 목록. `stations`가 `호선|statn_id → {station_id(우리 id), name}`. `scopes`는 단위별 상태(`suspect`·`retraining` 등), `modes`는 호선별 `train_no`/`slots`.
- 같은 열차 번호가 날마다 같은 시각에 다니는가(평일 2일, ±5분): 5~9호선·공항철도·우이신설선·신림선·서해선·경강선 98~100%, 3호선·수인분당선·경의중앙선 92~96%, 1·4호선 83~84%, **2호선 57%, 신분당선 21%**. B1은 80% 미만인 호선을 자동으로 `slots`(번호 없이 시각 묶음)로 만든다. 따라서 **신분당선은 열차 번호로 역끼리 맞출 수 없다** → 구간 시간(B2)으로 계산한다. 2호선은 공식 시간표가 있어 상관없다.
- B2(`ml/b2.py`)는 `hops`(`호선|방향|역A|역B|급행` → 중앙값 등, 요일·시간대별 세분 포함), 정차 시간 `dwell`을 낸다. 지금 밤 작업은 B1만 만든다.
- 결과물 크기: 지금 48KB(칸 0개). 칸이 다 차면 수 MB로 예상 → gzip으로 올린다.

## 4. 설계

### 4.1 VM: 수·일 내보내기

- 새 타이머 `subway-ml-publish`(수·일 03:30, 밤 작업 02:40 뒤). 하는 일:
  1. B2를 만든다(`ml.b2`, 최근 창). B1은 밤 작업이 만든 것을 쓴다.
  2. 둘을 gzip하고, 두 파일의 sha256·`built_at`·`as_of`를 담은 `manifest.json`을 만든다.
  3. GitHub 릴리스 `measured-timetable`(태그 같음, 없으면 만든다)의 자산을 바꾼다: 같은 이름의 옛 자산을 지우고 새로 올린다. 순서는 데이터 두 개 → manifest 마지막(서버는 manifest를 보고 받으므로, 중간 상태를 안 본다).
- 토큰: VM `.env`의 `GITHUB_RELEASE_TOKEN`(사용자가 만든다. fine-grained, 이 저장소만, Contents 읽기·쓰기). 로그·예외에 값을 남기지 않는다. 없으면 내보내기만 건너뛰고(종료 코드 2) Discord로 알린다(`run_with_alert`).
- 실패하면 Discord 알림. 옛 자산은 그대로 남아 서버는 지난 것을 계속 쓴다.

### 4.2 서버: 받기

- `MeasuredStore`(서버 메모리). 시작할 때(백그라운드, 시작을 막지 않음)와 **6시간마다**(요청이 올 때 확인하는 방식, 무료 서버가 잠들므로 별도 스케줄러 없음) manifest를 받아 `built_at`이 바뀌었으면 두 파일을 받는다.
- 주소는 공개 릴리스 내려받기 주소(`https://github.com/klanary/subway_easy/releases/download/measured-timetable/…`). 설정 `MEASURED_BASE_URL`로 바꿀 수 있게 한다(테스트·비우면 끔).
- 검증: sha256 일치, `version`·`kind` 확인, JSON 형식. 하나라도 틀리면 **지난 것을 유지**하고 경고 로그.
- 신선도: `as_of`가 14일보다 오래되면 쓰지 않는다(VM이 멈춘 경우).

### 4.3 서버: 조회 함수 (작업 2·3도 씀)

- `departures(station_id, line, direction, after, count)` → 실측 출발 목록. B1 키의 방향 0/1을 서버 방향 이름으로(2호선 내선·외선, 그 밖 상행·하행), statn_id를 `stations`로 우리 id에 맞춘다. 요일 구분은 서버의 `week_tag`와 같은 규칙(평일 1·토 2·일·공휴일 3). 05시 전 전날, 모자라면 다음 날(공식 시간표와 같은 규칙).
- 거르기: `n_days`가 하한 미만인 항목, `scopes`에서 `retraining`인 단위(2026-11-22부터 `suspect`는 거르지 않는다, `docs/ml/timetable-changes.md`), 종착역이 이 역인 항목을 뺀다.
- `arrival_at(line, direction, train_no, station_id, day)` → 그 열차가 다른 역에 닿는 시각(`train_no` 방식 호선만). 없으면 None(서지 않는 급행이거나 관측 없음).
- `hop_seconds(line, direction, from_id, to_id, express, day_type, hour)` → B2 중앙값(시간대 → 요일 → 전체 순으로 있는 것). 이웃 역이 아니면 사이 구간을 더한다(작업 2에서 쓰임).

### 4.4 서버: 응답에 쓰기

- `/v1/stations/{id}/timetable`: 공식 시간표가 비고 그 노선이 1~9호선이 아니면 실측으로 채운다. 응답에 `source: "official" | "measured" | "none"`을 더한다(기존 필드는 그대로).
- `/arrivals`: 실시간이 없는 방향 채우기에서 공식이 없으면 실측으로. 그룹 `source`에 `"measured"`를 더한다.
- `/routes`의 환승 열차·`departAt` 첫 열차: 같은 `TimetableService` 경유라 자동으로 실측을 쓴다. `TransferTrain.source`에 `"measured"`가 올 수 있다.

### 4.5 앱

- 출처 표시만: `"measured"`면 "실측", `"timetable"`·`"official"`이면 지금처럼 "시간표". 역 시트의 "시간표가 없는 노선" 안내는 실측도 없을 때만.
- 모르는 `source` 값이 와도 죽지 않게(지금 DTO가 문자열이면 그대로) 확인한다.

## 5. 테스트

- VM: 내보내기 스크립트를 GitHub API 흉내(respx)로 — 자산 바꾸기 순서(manifest 마지막), 토큰이 로그에 없음, 토큰 없으면 2.
- 서버: 작은 결과물 픽스처(B1 칸 몇 개, B2 구간 몇 개)로 — 방향·역 id 변환, 하한·scope 거르기, 자정 넘김, 열차 번호로 다른 역 시각, slots 호선은 `arrival_at` None, 검증 실패 시 지난 것 유지, 14일 넘으면 안 씀, 받기 실패해도 요청은 정상.
- 통합: 신분당선 `/timetable`이 실측으로 차고 `source: "measured"`, 5호선은 여전히 `official`.
- 앱: 출처 문구 단위 테스트.

## 6. 사용자가 할 일

1. GitHub에서 fine-grained 토큰 만들기(이 저장소만, Contents 읽기·쓰기), VM `.env`에 `GITHUB_RELEASE_TOKEN=` 넣기.
2. 배포 뒤 Render Manual Deploy(서버 코드 변경).

## 7. 구현자에게 맡긴 것

- 내보내기 시각(03:30 근처)과 받기 주기(6시간)는 바꿀 수 있다.
- B2를 만드는 창(최근 며칠)은 B1의 `WINDOW`와 맞추는 것을 기본으로.
- gzip 여부와 파일 이름.

## 8. 제가 정한 것(확인 부탁)

- 1~9호선은 실측이 있어도 공식 시간표를 쓴다.
- 받기 주기 6시간, 신선도 14일.
- 새 출처 이름 `"measured"`, 앱 문구 "실측".
- `/timetable` 응답에 `source` 필드를 더한다.
