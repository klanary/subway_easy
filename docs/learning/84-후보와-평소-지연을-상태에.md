# 84. 변경 상태에 공식 시간표 후보와 평소 지연

- 무엇을 만들었나: `server/ml/changes.py`의 상태 파일에 `candidates`(공식 시간표가 달라진 단위)와 `delays`(호선·방향별 평소 지연)를 더하고 판 번호를 2로 올렸다. 새 파일 `server/ml/official.py`에 차이 목록을 후보로 들이는 `ingest_candidates`와 오래된 후보를 버리는 `prune_candidates`를 뒀다. 판정에 쓸 기준값 이름을 `Thresholds`에 더했다.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 후보를 별도 파일에 두면 받기(`b0`)와 밤 작업 둘이 같은 파일을 쓰게 된다. 받기는 "무엇이 달라졌나"만 적고(차이 목록), 후보의 상태는 밤 작업만 쓰는 상태 파일에 뒀다.
  - 후보는 `(단위, 받은 날)`로 구별해 같은 항목을 다시 들여도 늘지 않는다. 밤 작업을 같은 밤에 다시 돌려도 결과가 같아야 하기 때문이다.
  - 같은 단위에 새 후보가 오면 앞의 열린 후보는 닫는다. 옛 시간표가 둘이면 어느 것과 견줄지 모호해진다.
  - 비율 하한(지금의 10%)은 두지 않았다. 열차 한 대만 바뀌어도 후보로 들이고, 판정에서 표가 모자라면 보류될 뿐이다.
- 막혔던 점과 해결:
  - 판 1 상태 파일(VM에 이미 있다)을 그대로 읽어야 한다. 두 키가 없으면 빈 값으로 읽게 하고 테스트로 고정했다.
  - 차이 목록의 항목이 깨져 있어도 밤 작업이 멈추면 안 된다. 읽을 수 없는 항목은 경고만 남기고 건너뛴다.
- 예상 면접 질문과 내 답:
  - Q. 판정 로직을 왜 `changes.py`가 아니라 새 파일에 뒀나?
  - A. `changes.py`는 이미 750줄이고 "실측끼리 견주는 감지"를 맡는다. "공식 시간표 둘과 견주는 판정"은 입력도 규칙도 달라 따로 읽히는 편이 낫다. 상태의 모양(`Candidate`)만 `changes.py`에 두어 저장·읽기가 한곳에 있게 했다.
