# 44. 역 실시간 도착 API

> Claude Code가 쓴 초안이다. 본인이 직접 고쳐 쓴다(스펙 12절).

- 무엇을 만들었나: 서울시 실시간 도착정보를 부르는 `SeoulSubwayClient`, 응답을 호선·방향별 다음 열차 2대로 정리하는 `ArrivalService`, `GET /v1/stations/{역}/arrivals?line=&towards=`.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 서울시 응답은 20초 동안 캐시한다. 여러 사용자가 같은 역을 봐도 외부 호출은 한 번이고, 하루 1,000회 한도의 80%를 넘으면 캐시 시간이 3배로 늘어난다.
  - 외부 호출이 실패하면 예전 값을 `stale: true`로 돌려준다. 빈 화면보다 "조금 전 정보"가 낫다.
  - 이미 역을 떠난 열차("OO 출발")는 뺀다. 실제 샘플에 13분 전에 떠난 열차가 그대로 남아 있었다.
  - 남은 시간은 캐시에 넣지 않고 응답할 때마다 다시 계산한다. 캐시에는 원본을 두고, "지금" 기준으로 생성 시각 이후 지난 시간을 뺀다.
  - 이름이 같은 다른 역(양평)은 서울시가 두 역의 열차를 함께 주므로, 그 역의 호선만 남긴다.
- 막혔던 점과 해결:
  - 서울시 API는 오류도 HTTP 200으로 준다. 정상은 `errorMessage` 안에 `INFO-000`, 오류는 `errorMessage` 없이 `code`가 바로 온다. 실제 응답을 받아 보기 전에는 몰랐던 형식이라, 두 형식에서 코드를 꺼내는 함수를 따로 두었다.
  - 새벽에는 모든 역이 "데이터 없음"(`INFO-200`)이다. 오류가 아니라 빈 목록으로 돌려준다.
  - 계획의 테스트는 홍대입구 샘플을 썼지만 낮에만 받을 수 있어, 공식 샘플 키로 받은 '서울'역 실제 응답(4개 호선)으로 테스트를 만들었다.
- 예상 면접 질문과 내 답:
  - Q. 캐시 때문에 남은 시간이 틀리지 않나? A. 원본을 캐시하고 남은 시간은 응답 시점에 다시 계산하므로 20초 묵은 값이 그대로 나가지 않는다.
  - Q. 한도 초과는 어떻게 아나? A. 서울시가 본문 코드로 알려 주면 그날은 더 부르지 않도록 표시하고, 캐시가 있으면 `stale`로, 없으면 503을 준다.
