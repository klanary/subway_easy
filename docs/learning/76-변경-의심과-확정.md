# 76. 변경 의심·확정 상태와 기록

- 무엇을 만들었나: `server/ml/changes.py`의 뒷부분. `ChangeState`(상태 파일 `ml_data/change_state.json`)가 단위별 기록(`ChangeRecord`: 의심·확정·해제)을 들고, `detect_day`가 하루치를 판단해 상태를 옮긴다. 손으로 확정·되돌리는 `mark`·`clear`, 사람이 읽는 줄로 바꾸는 `render`, 기록 파일(`changes.md`)에 덧붙이는 `append_log`, B1 결과물에 상태를 적는 `annotate`, 그리고 CLI `python -m ml.changes show|mark|clear`.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 확정 조건은 "이틀 연속 의심"이 아니라 **"둘째 날이 첫 의심일과 서로 맞음"**이다. 큰 지연은 이틀 연속 올 수 있지만 모양이 다르다. 날끼리 원래 잘 안 맞는 노선을 위해 "3일 연속이면 확정"을 따로 두었다.
  - 수집이 빈 시간대는 의심도 해제도 하지 않는다. 수집기가 멈추면 열차가 사라진 것처럼 보이기 때문이다. 네 번 판단하지 못하면 의심을 내려놓는다.
  - 확정된 단위의 기준표는 변경일 이후로 다시 만든다. 그래야 확정한 변경을 다음 날 또 의심하지 않는다.
  - 상태 파일은 임시 파일에 다 쓴 뒤 `os.replace`로 바꾸고, 바꾸기 전 것을 `.prev`로 남긴다. 읽을 수 없으면 예외를 내고 덮어쓰지 않는다. 상태를 잃으면 확정된 변경일을 모두 잃기 때문이다.
  - 같은 날을 두 번 판단해도 결과가 같게 했다(`checked`에 호선·요일 구분별 마지막 판단일). 밤 작업이 다시 돌거나 따라잡을 때 필요하다.
- 막혔던 점과 해결:
  - 테스트 하나가 실제 약점을 드러냈다. 7일 가운데 이틀이 크게 늦자 그 호선이 "열차 번호가 날마다 다르다"로 분류되어 번호 신호가 꺼졌고, 셋째 날의 10분 지연이 배차 간격만큼 밀려 시각 짝짓기에서는 정상으로 보였다. 원인은 번호 안정성을 "최대 − 최소 ≤ 300초"로 재던 것이다. "관측한 날의 70% 이상이 중앙값에서 300초 안"으로 바꿨다.
  - 번호 없이 시각만 보는 노선은 배차 간격만큼 밀린 변화를 볼 수 없다(06:00 열차가 06:06에 오면 06:06 열차처럼 보인다). 2호선이 여기 해당하고, 열차 수·급행 비율 신호만 사실상 작동한다.
- 예상 면접 질문과 내 답:
  - Q. 잘못 확정하면 어떻게 되나?
  - A. 그 단위는 과거를 버리고 2~3일치로 시각을 다시 만든다. 그래서 처음에는 관찰 모드로 기록만 하고, 기준값을 실제 자료로 맞춘 뒤에 적용을 켠다. 켠 뒤에도 `clear`로 되돌릴 수 있다.
