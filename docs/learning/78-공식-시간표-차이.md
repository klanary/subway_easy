# 78. 공식 시간표 다시 받아 차이 보기

> Claude Code가 쓴 초안이다. 본인이 직접 고쳐 쓴다(스펙 12절).

- 무엇을 만들었나: `server/ml/b0.py`에 `diff_caches`(두 시간표 캐시의 차이를 단위별 비율로), `refresh`(전부 새로 받아 지난 캐시와 견주고 캐시를 바꿈), `B0.departures`, CLI `python -m ml.b0 --refresh`(차이를 `ml_data/official_diff.json`에 씀). `server/ml/changes.py`에 `load_official_changed`(그 파일에서 10% 이상 달라진 단위)와 `official_fit`(확정된 변경을 공식 시간표가 따라왔는지 관측과 직접 견줌). 밤 작업이 둘 다 쓴다.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 공식 시간표가 바뀐 단위에서 의심이 생기면 하루 만에 확정한다. 실측만으로는 이틀이 필요한데, 2~9호선은 공식 쪽 증거가 하나 더 있는 셈이다.
  - "공식 시간표가 아직 옛것인가"는 지난주와의 차이로 판단하지 않는다. 차이가 없다는 것은 "안 바뀌었다"일 수도, "우리가 처음 받기 전에 이미 바뀌었다"일 수도 있다. 그래서 공식 시간표를 기준표로 놓고 그 날 관측과 직접 견준다(`official_fit`).
  - `refresh`는 새 폴더(`.next`)에 전부 받은 뒤에만 폴더를 바꾼다. 하나라도 실패하면 아무것도 바꾸지 않는다. 절반만 새것인 캐시는 차이 계산을 틀리게 만든다.
  - 지난 캐시는 날짜를 붙여 최근 4개만 남긴다. 시험 기간 안에 공식 시간표가 바뀌었을 때 옛 시간표로 평가를 다시 돌릴 여지를 둔다.
- 막혔던 점과 해결:
  - 계획의 `refresh`에는 역 코드 → 호선 표가 인자에 없었는데, 단위를 만들려면 호선이 필요하다. `lines_by_code` 인자를 더했다.
  - `changes`가 `b0`를 가져오고 `nightly`가 둘을 가져온다. 순환하지 않게 `b0`는 `changes`를 모르게 두었다(단위 정의만 `scopes`에서 함께 쓴다).
  - 이 도구는 일반 인증키(`SEOUL_OPENAPI_KEY`)를 쓴다. VM `.env`에는 그 키가 없으므로 지금은 개발 PC에서 돌려야 하고, 어디서 돌릴지는 사용자가 정할 일로 남겼다.
- 예상 면접 질문과 내 답:
  - Q. 여러 파일을 한꺼번에 바꿀 때 중간에 실패하면 어떻게 하나?
  - A. 옆 폴더에 새 것을 전부 만든 다음 폴더 이름을 바꾼다. 실패하면 새 폴더만 지우면 되고, 원래 것은 손대지 않았으므로 되돌릴 것이 없다.
