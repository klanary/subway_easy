# 65. 수집 DB 백업과 운영 문서

> Claude Code가 쓴 초안이다. 본인이 직접 고쳐 쓴다(스펙 12절).

- 무엇을 만들었나: `server/ml/backup.py`(`python -m ml.backup`)와 `docs/ml/collector.md`. 백업은 DB 전체를 `collector-YYYYMMDD.sqlite.gz`로 복사하고, 최근 7개만 남기고, 수집 DB에서 14일 넘은 raw 응답을 지운다. 문서에는 VM 준비, `systemd` 서비스와 백업 타이머, 백업을 PC로 옮기는 `scp`, Windows 작업 스케줄러 대안을 적었다.
- 왜 이렇게 했나 (검토한 대안과 고른 이유):
  - 파일을 그냥 복사(`cp`)하면 수집기가 쓰는 중에 깨진 사본이 나올 수 있다. SQLite의 온라인 백업(`Connection.backup`)은 쓰는 중에도 일관된 사본을 만든다. 수집 DB는 WAL 모드라 백업이 읽는 동안 수집기가 계속 쓴다.
  - 임시 이름으로 다 쓴 뒤 `replace`로 이름을 바꾼다. 중간에 죽어도 쓰다 만 파일이 백업처럼 보이지 않는다.
  - raw 보관 기간(14일)과 백업 수(7개)는 설계 §10에서 구현자에게 맡긴 값이다. raw는 크지만 "파싱 규칙을 바꿔 다시 만들기"에 필요한 기간만 있으면 된다. 오래된 것은 PC로 옮긴 백업에 남는다.
  - 순서는 백업 → 오래된 백업 지우기 → raw 지우기. 백업 파일에는 항상 지우기 전 상태가 들어간다.
  - 백업 시각은 02:10. 수집기가 쉬는 01:00~05:00 안이라 그날 운행이 다 들어간다. 파일 이름의 날짜는 어제다.
- 막혔던 점과 해결:
  - 수집기의 시간 계산은 코드 안에서 KST로 하지만 `systemd` 타이머는 VM 시간대를 따른다. 문서에 `timedatectl set-timezone Asia/Seoul`을 넣었다.
  - Windows 작업 스케줄러는 한 작업에 트리거 두 개(로그온, 매일 04:55)를 걸려면 `schtasks`로는 안 되고 `Register-ScheduledTask`를 써야 한다. `-MultipleInstances IgnoreNew`로 이미 돌고 있으면 새로 띄우지 않게 했다.
- 예상 면접 질문과 내 답:
  - Q. 돌고 있는 SQLite를 어떻게 안전하게 백업하나?
  - A. 온라인 백업 API를 쓴다. 페이지 단위로 복사하면서 원본이 바뀌면 그 부분을 다시 복사해, 끝났을 때 한 시점의 일관된 사본이 된다. 파일 복사는 WAL 파일과 본 파일의 시점이 어긋날 수 있다.
