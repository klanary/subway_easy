## 1. 배경과 목표

### 1.1 문제
서울시 실시간 도착정보 API만으로는 도착 시간이 거칠다. 2026-11-05에 받은 실제 응답에서 다음을 확인했다.
- 도착 예정 초(`barvlDt`)가 대부분 0이라, 남은 시간을 안내 문구("전역 도착" 등)에 붙인 고정값으로 추정하게 된다.
- 이미 역을 떠난 열차 기록이 18분 동안 남아 있었다(`recptnDt` 13:41, 다른 기록 13:59).
- 두 번째 열차가 "홍대입구 도착"인데 현재 위치(`arvlMsg3`)는 "공덕", 순번(`ordkey`)은 두 번째로 서로 맞지 않았다.

카카오 앱은 운영사와 제휴한 데이터를 쓰는 것으로 보이며, 우리가 쓸 수 있는 공개 데이터는 서울시 API뿐이다.

### 1.2 목표
- **⑬ 위치 결합 도착 시간:** 역 상세와 경로 카드의 "다음 열차 N분"을, 같은 열차의 실시간 위치와 역 사이 소요 시간으로 다시 계산해 더 정확하게 한다. 승차 전 알림(⑦)도 같은 계산을 쓰므로 함께 정확해진다.
- **⑪ 하차 알림 실시간 보정:** 탄 열차를 따라가며 내릴 역 도착 시각을 다시 계산해 하차·환승 알림 시각을 맞춘다.
- **⑭ 탑승 열차 정하기:** 탄 열차를 계획한 열차, 위치 자동 감지, 직접 고르기 순서로 정한다.

## 4. 외부 데이터

### 4.1 서울시 지하철 실시간 열차 위치정보 (`realtimePosition`)
서울 열린데이터광장 데이터셋 페이지(2026-11-05 확인)의 내용이다.

- **요청:** `http://swopenAPI.seoul.go.kr/api/subway/{키}/json/realtimePosition/0/200/{호선명}` (호선명 예: `5호선`). 한 번에 최대 1,000건까지 받을 수 있다(ERROR-336).
- **키:** 위치정보 전용 인증키. 서버 환경 변수 `SEOUL_POSITION_API_KEY`. 일일 한도 기본 1,000회(`SEOUL_POSITION_DAILY_LIMIT`).
- **출력 필드:** `subwayId`, `subwayNm`, `statnId`, `statnNm`(지금 역), `trainNo`(열차 번호), `lastRecptnDt`(날짜 `YYYYMMDD`), `recptnDt`(시각 `YYYY-MM-DD HH:MM:SS`), `updnLine`(`"0"` 상행·내선, `"1"` 하행·외선), `statnTid`·`statnTnm`(종착역), `trainSttus`(`"0"` 진입, `"1"` 도착, `"2"` 출발, `"3"` 전역출발), `directAt`(`"1"` 급행, `"0"` 아님, `"7"` 특급), `lstcarAt`(`"1"` 막차)
- **응답 코드:** 도착정보 API와 같다(`INFO-000` 정상, `INFO-200` 데이터 없음, `ERROR-3xx` 요청 오류, `ERROR-5xx/6xx` 서버 오류). "데이터 없음"은 오류가 아니라 빈 목록이다.
- **알려진 문제 (데이터셋 댓글):** 6호선 위치가 자주 빠짐, 0시 30분 이후 1~8호선 정보가 사라짐, 큰 페이지로 조회해도 열차가 일부 빠지는 경우가 있음.

### 4.2 실시간 도착정보에서 새로 쓰는 필드
2026-11-05 실제 응답과 데이터셋 명세로 확인했다.
- `btrainNo`: 열차 번호. 위치정보의 `trainNo`와 같은 열차를 잇는 열쇠다.
- `ordkey`: 상하행코드(1자리) + 순번(1자리) + 첫 도착예정 정류장까지 남은 정거장 수(3자리) + 목적지 + 급행여부(1자리). 예: `02001인천공항2터미널0`
- `statnFid`·`statnTid`: 이전·다음 역 ID, `statnId`: 이 역 ID
- `arvlCd`: `0` 진입, `1` 도착, `2` 출발, `3` 전역출발, `4` 전역진입, `5` 전역도착, `99` 운행중
- `updnLine`은 도착정보에서는 문자열(`상행`, `하행`, `내선`, `외선`)이고 위치정보에서는 코드(`0`, `1`)다.
- **공식 안내:** 지금 시각과 `recptnDt`의 차이만큼 열차가 더 진행한 것으로 보정해야 한다(예: 2분 차이면 도착 정보를 2분 당기거나 한 역 더 간 것으로 본다).
- **알려진 문제:** `recptnDt`가 오래되거나(실측 18분) 미래(신분당선 최대 +160초)로 올 수 있다. 5호선 천호역 데이터 누락, 강일역은 항상 "강일 도착"이라는 보고가 있다.
- **역 이름 예외 (공식 목록):** 응암 → 응암순환(상선), 공릉 → 공릉(서울산업대입구), 춘의 → 춘의, 남한산성입구 → 남한산성입구(성남법원, 검찰청), 대모산입구 → 대모산, 천호 → 천호(풍납토성), 몽촌토성 → 몽촌토성(평화의문)

### 4.3 정적 데이터 (준비물)

| 원본 파일 (`server/data/raw/`) | 출처 | 쓰는 것 |
|---|---|---|
| `realtime_station_info.xlsx` | 서울 열린데이터광장 "서울시 지하철 실시간 도착정보" 페이지의 파일내려받기 `실시간도착_역정보(20260902).xlsx` | 실시간 API 역 ID(`statnId`)와 역 이름·호선 |
| `metro_station_times.(csv\|xlsx)` | 공공데이터포털 "서울교통공사 역간거리 및 소요시간" | 5·6호선 역 순서와 역 사이 소요 시간 |

- 두 번째 파일이 없거나 5·6호선 구간이 빠져 있으면 `scripts/collect_run_times.py`로 대신한다. 위치정보를 30초마다 60~120분 관찰해, 같은 열차가 A역 "출발"에서 다음 B역 "도착"까지 걸린 시간의 중앙값을 역 사이 시간으로 쓰고, 관찰한 순서로 역 순서를 정한다.

## 5. 노선 표 (`line_topology.json`)

형식 (ID와 시간 값은 예시):

```json
{
  "version": 1,
  "dwellSec": 30,
  "lines": {
    "5호선": {
      "stations": {"1005000xxx": {"stationId": "공덕", "name": "공덕"}},
      "edges": [{"from": "1005000xxx", "to": "1005000yyy", "sec": 90}]
    }
  }
}
```

- `stations`: 실시간 API 역 ID → 우리 역 id(1차 스펙 6.5의 정규화 이름)와 표시 이름. 우리 역 id와 실시간 역 ID 사이의 변환은 이 표로만 한다.
- `edges`: 한 방향 화살표. 보통 구간은 양쪽 방향 화살표를 둘 다 둔다. 6호선 응암 순환 구간(응암 → 역촌 → 불광 → 독바위 → 연신내 → 구산 → 응암)은 한쪽 방향만 둔다. 순환을 돈 뒤의 응암은 순환에 들어가기 전 응암과 다른 칸(별도 노드)으로 둬서, 경로가 순환 구간을 지나가게 한다.
- `loopEnds`(호선별, 선택): `{"순환 뒤 노드 id": "원래 실시간 역 ID"}`. 순환 뒤 노드는 `stations`에 없고 화살표에만 나온다. 종착역(`statnTid`)이 이 역이면 경로의 끝을 순환 뒤 노드로 잡고, 경로에서는 원래 역 ID로 보인다.
- 5호선 강동역에서는 하남검단산 쪽(길동)과 마천 쪽(둔촌동) 화살표가 둘 다 나간다.
- `sec`: 앞 역을 출발해 다음 역에 도착할 때까지의 시간. 원본 시간이 정차 시간을 포함하면 `dwellSec`을 0으로 둔다. 어느 쪽인지는 원본 파일 설명으로 정하고 결과를 `docs/analysis/api-verification.md`에 적는다.
- **경로 찾기:** 열차의 지금 역에서 종착역(`statnTid`)까지 화살표를 따라가는 최단 경로를 구하고, 목표 역이 그 경로 위에 있을 때만 남은 시간을 계산한다. 종착역이 방향과 갈래를 함께 정해 주므로 상행·하행을 따로 판단하지 않는다.

## 6. 서버

### 6.1 구성 (1차 스펙 6.9 구조에 더하는 파일)

| 파일 | 역할 |
|---|---|
| `app/clients/seoul_position.py` | `SeoulPositionClient.fetch_positions(line_name) -> list[dict]`: 위치정보 API 호출과 응답 코드 처리만 |
| `app/services/topology.py` | `LineTopology`: 노선 표 읽기, 역 ID 변환, 종착역까지의 경로와 누적 시간 |
| `app/services/eta.py` | `eta_from_position(...)`, `eta_from_arrival(...)`: 남은 시간 계산 (순수 함수) |
| `app/services/arrival_fusion.py` | `fuse_trains(...)`: 도착 정보와 위치를 잇고 계산 방식을 고른다 (순수 함수) |
| `app/services/train_service.py` | 역 근처 열차 목록, 특정 열차의 남은 시간 |
| `app/api/trains.py` | 6.3절의 새 API 두 개 |
| `scripts/build_topology.py`, `scripts/collect_run_times.py`, `scripts/measure_accuracy.py` | 노선 표 만들기, 소요 시간 관찰(대안), 정확도 측정 |

실시간 도착 API의 `ArrivalService`(P2 Task 9)는 묶기·정렬 전에 `fuse_trains`를 부른다.

### 6.2 계산 규칙

**위치로 계산 — `eta_from_position(topology, position, target_statn_id, now) -> int | None`**
1. 지금 역(`statnId`)에서 종착역(`statnTid`)까지의 경로에 목표 역이 없으면 `None`(이미 지났거나 다른 갈래).
2. 지금 역에서 목표 역까지 화살표 시간의 합 + 사이 정차 역마다 `dwellSec`.
3. 열차 상태로 보정한다 (지금 역 기준, 값은 측정으로 고칠 상수):

| `trainSttus` | 뜻 | 보정 |
|---|---|---|
| `3` 전역출발 | 이전 역을 떠나 지금 역으로 오는 중 | + (이전 역 → 지금 역 화살표 시간 × 0.5) |
| `0` 진입 | 지금 역에 들어오는 중 | + 15초 |
| `1` 도착 | 지금 역에 서 있음 | 목표가 지금 역이면 0. 아니면 + (`dwellSec` × 0.5) |
| `2` 출발 | 지금 역을 막 떠남 | 목표가 지금 역이면 `None`(지남). 아니면 − 10초 |

4. `now − recptnDt`(0 이상)를 뺀다. 결과가 음수면 0.

**도착 정보로 계산 — `eta_from_arrival(item, now) -> int | None`** (1차 스펙 6.7에 더하는 규칙)
- 안내 문구로 추정한 값에서도 `now − recptnDt`를 뺀다(공식 안내).
- `recptnDt`가 지금보다 300초 넘게 지난 기록은 버린다(목록에서 뺀다).
- `recptnDt`가 미래면 지금 시각으로 본다.
- "OO 출발" 열차를 빼는 규칙(1차 스펙 6.7 규칙 5)은 그대로다.

**결합 — `fuse_trains(items, positions, topology, station, now)`**
1. 노선 표에 없는 호선이면 모든 열차를 도착 정보로 계산한다.
2. 도착 기록마다 같은 호선에서 `trainNo == btrainNo`인 위치를 찾는다.
3. 위치가 있고 `now − 위치.recptnDt ≤ 180초`면 위치로 계산한다. 결과가 `None`이면 그 기록을 뺀다.
4. 그 밖은 도착 정보로 계산한다.
5. 열차마다 `basis`(`"position"` 또는 `"arrival"`)와 `trainNo`를 붙이고, 1차 스펙 6.2 규칙대로 묶어 남은 시간순(`null`은 뒤) 2대씩 남긴다.

위치정보 호출이 실패하거나 한도에 닿아도 오류를 내지 않고 모두 도착 정보로 계산한다(경고 로그와 지표만 남긴다).

### 6.3 API

**역 도착 정보 (1차 스펙 6.2 변경):** 열차 항목에 `trainNo`(문자열, 없으면 `null`)와 `basis`를 더한다. 기존 앱은 모르는 칸을 무시하므로 깨지지 않는다.

**`GET /v1/lines/{line}/trains?station={역 id}&toward={다음 역 id}`** — 그 역 앞뒤 3정거장 안의 열차 (직접 고르기 목록과 자동 감지 후보). `toward`(선택)를 주면 `station`에서 `toward` 쪽으로 가는 열차만 돌려준다. 방향 판단은 노선 표가 있는 서버가 한다.

```json
{
  "line": "5호선",
  "updatedAt": "2026-11-05T08:01:30+09:00",
  "stale": false,
  "trains": [
    {"trainNo": "5123", "stationId": "공덕", "stationName": "공덕", "state": "DEPARTED",
     "direction": "하행", "destination": "하남검단산", "isExpress": false, "isLast": false, "etaSec": null,
     "stopsFromStation": 1}
  ]
}
```

- `state`: `APPROACHING`(진입), `ARRIVED`(도착), `DEPARTED`(출발), `LEFT_PREVIOUS`(전역출발)
- `etaSec`: 그 역까지 남은 초. 이미 지났으면 `null`
- `stopsFromStation`: 열차의 지금 역이 `station`에서 몇 정거장 떨어졌는지. 아직 오는 중이면 음수, 그 역이면 0, 지나갔으면 양수(열차 진행 방향 기준). 목록은 (`stopsFromStation`, 진행 순서 LEFT_PREVIOUS → APPROACHING → ARRIVED → DEPARTED) 순서다. 앱의 자동 감지가 "탈 역 다음 2정거장 안"을 이 값으로 판단한다.
- 노선 표에 없는 호선: 404 `NOT_FOUND`, reason `LINE_NOT_SUPPORTED`. 없는 역: 404 `NOT_FOUND`

**`GET /v1/trains/{trainNo}?line={line}&to={역 id}`** — 탄 열차가 내릴 역까지 남은 시간 (탑승 중 30초마다)

```json
{"trainNo": "5123", "line": "5호선", "found": true, "stationId": "공덕", "state": "DEPARTED",
 "etaSec": 540, "updatedAt": "2026-11-05T08:01:30+09:00", "stale": false}
```

- 지금 위치 목록에 그 열차가 없으면 200과 `found: false`(오류 아님). `to`를 이미 지났으면 `etaSec: null`.

### 6.4 캐시·한도·지표
- 위치정보 캐시: 키는 호선 이름, 유효 시간 30초. 한도 80% 이상이면 ×3, 만료 항목 보관 규칙은 1차 스펙 6.4와 같다(다만 180초 넘은 위치는 결합에 쓰지 않는다).
- 호출 한도 보호: `seoulPosition`(기본 1,000회/일, 한국 시간 00:00 초기화).
- `/v1/metrics`: `upstream.seoulPosition`과 `fusion: {"position": n, "arrival": m}`(시작 뒤 계산 방식별 열차 수)를 더한다.
- 로그의 키 가리기는 1차 스펙 6.8 규칙(`/api/subway/{키}/` 경로)을 그대로 쓴다.

## 7. 앱

### 7.1 탄 열차 정하기 (⑭)
다음 순서로 정한다.

1. **계획한 열차:** 승차 전 알림의 계획(`TrainPlan`)에 열차 번호를 저장해 둔다. 열차 번호 없이 탑승으로 넘어가면 이 번호를 쓴다(출처 `PLANNED`).
2. **위치 자동 감지 (`BoardingDetector`, 순수 함수)**
   - **켜지는 때:** 통학 세션이 대기 단계일 때(세션 서비스가 돌고 있으니 화면이 꺼져도 된다), 또는 경로 상세 화면이 보이고 그 경로의 첫 지하철 단계가 노선 표에 있는 호선일 때.
   - **위치 받기:** `FusedLocationProviderClient`, 높은 정확도, 10초 간격. 정확도가 1,000m보다 나쁜 위치는 버린다.
   - **판단 규칙:** 탈 역 300m 안의 위치가 있었고, 그 뒤 탈 역에서 500m 넘게 떨어지면서 탈 역보다 다음 역에 더 가까운 위치가 나오고, 두 위치 사이 속도가 시속 15km 이상이면 "탑승"으로 본다. 걷기로는 이 조건을 넘지 못한다.
   - **열차 고르기:** 6.3의 근처 열차 목록을 `toward = 그 단계의 다음 역`으로 받아, 탈 역을 막 지난 열차(탈 역에서 출발 상태이거나 탈 역 다음 2정거장 안에 있고 탈 역까지 `etaSec`이 `null`인 열차) 가운데 탈 역에 가장 가까운 열차로 정한다(출처 `AUTO`). 그런 열차가 없으면 직접 고르기를 연다.
   - **세션 대기 중 감지:** 누르지 않아도 탑승 단계로 넘어가고, "OO행 열차에 탄 것으로 보여요" 알림에 [다른 열차였어요] 버튼을 단다.
   - **경로 상세만 보던 중 감지:** "OO행에 타셨나요? [하차 알림 시작] [아니에요]"를 화면 안에서 묻는다.
3. **직접 고르기:** 세션 화면과 알림의 [다른 열차였어요]에서 근처 열차 목록("OO행 · 지금 XX역")을 보여 주고, 고르면 그 열차로 정한다(출처 `MANUAL`). 언제든 바꿀 수 있다.

위치 권한이 없으면 자동 감지를 끄고 1·3만 쓴다.

### 7.2 탑승 중 추적 (⑪)
- **상태:** 탑승 상태(`Riding`)에 `tracking`(지금 지하철 단계 번호, 호선, 열차 번호, 내릴 역, 연속 실패 수, 끊김 여부)을 더한다.
- **조회:** `tracking`이 있으면 30초마다 `GET /v1/trains/{열차번호}`를 부른다.
- **새 사건 3개 (상태 머신):**
  - `TrainIdentified(stepIndex, trainNo, source)`: 추적을 시작하거나 열차를 바꾼다.
  - `TrainEtaUpdated(etaSec, receivedAt)`: 지금 지점의 새 하차 시각 = `receivedAt + etaSec`. 기존과 20초 넘게 다르면 이 지점과 이후 지점을 같은 만큼 옮기고, 아직 울리지 않은 알람을 다시 예약한다(알림 시각 = max(지금, 하차 시각 − 알림 시점)). `etaSec`이 `null`(지남)이면 바꾸지 않는다. 실패 수를 0으로 되돌린다.
  - `TrainLookupFailed`: 응답이 `found: false`이거나 호출이 실패하면 보낸다. 실패 수 +1. 3회 연속이면 끊김으로 표시한다(진행 중 알림 부제 "실시간 추적 끊김"). 알람은 마지막 시각을 유지한다. 그 뒤 `TrainEtaUpdated`가 오면 끊김 표시를 지운다.
- **환승:** 지금 단계의 하차 지점이 지나면 `tracking`을 비우고, 다음 지하철 단계의 열차를 7.1 방식(환승역을 탈 역으로)으로 다시 정한다. 정하기 전까지 이후 지점은 지금까지 옮겨진 시간표 기준이다.
- 노선 표에 없는 호선의 단계는 추적하지 않는다.

### 7.3 서비스와 권한 (1차 스펙 8.2·8.3·8.6 변경)
- 대기 단계의 포그라운드 서비스를 **세션 서비스**로 넓힌다. 대기 단계에서는 지금처럼 돌고, 탑승 단계에서는 추적이나 자동 감지가 필요한 동안만 돈다. 둘 다 필요 없으면 멈추고 알람만 남긴다(1차 스펙 8.3과 같은 상태).
- 서비스 유형은 `dataSync|location`, 매니페스트에 `FOREGROUND_SERVICE_LOCATION`을 더한다.
- 위치 권한은 "앱 사용 중에만 허용" 그대로다. 서비스는 화면에서 시작한 세션이나 앱 시작 복원 때만 켠다. 재부팅 복원에서는 켜지 않고 알람만 복원한다(1차 스펙 8.7 그대로).

### 7.4 데이터 모델과 API 변경
- `TrainDto`에 `trainNo: String? = null`, `basis: String? = null`
- 새 DTO `LineTrainsDto`, `TrainNearDto`, `TrainEtaDto`와 `ApiService.lineTrains(line, station, toward)`, `ApiService.trainEta(trainNo, line, to)`, 저장소 `TrainRepository`
- `TrainPlan`에 `trainNo: String? = null`

## 8. 정확도 측정 (S6)

`server/scripts/measure_accuracy.py`
- **인자:** `--stations`(5·6호선 역 id 목록, 사용자가 고름), `--minutes`(기본 60), `--interval`(기본 30초). 실제 키로 데스크톱에서 실행하며 배포 서버에는 부담을 주지 않는다.
- **매 회차:** 역마다 도착정보, 호선마다 위치정보를 받아, 역·열차 번호별로 "도착 정보만으로 예측한 도착 시각"과 "결합해서 예측한 도착 시각"을 기록한다.
- **실제 도착 시각:** 위치정보에서 그 열차가 그 역에서 처음 `trainSttus = "1"`(도착)로 보인 기록의 `recptnDt`.
- **보고서:** 방식별 건수, 절대 오차 중앙값, 상위 10% 오차를, 예측 시점이 도착 몇 분 전이었는지(0~2분, 2~5분, 5~10분)로 나눠 `docs/measurements/accuracy-YYYYMMDD.md`에 쓴다.
- **한도:** 60분·30초 간격·역 4곳·호선 2개면 도착정보 480회, 위치정보 240회를 쓴다. 통학하지 않는 시간(저녁·주말)에 실행한다.

**앱 (JUnit, 순수 함수 중심)**
- `BoardingDetector`: 탈 역 근처 → 다음 역 쪽 빠른 이동이면 감지, 걷는 속도는 감지 안 함, 정확도 나쁜 위치 무시, 후보가 없으면 직접 고르기, 여러 대면 탈 역에 가장 가까운 열차
- 상태 머신: 새 사건 3개, 20초 기준, 이후 지점 함께 옮기기, 이미 울린 알람은 다시 예약하지 않기, 3회 실패 끊김, 환승 때 추적 비우기
- 추적 조회 주기(가상 시간 30초)
